# 🎨 API Design: как проектировать API, чтобы им было приятно пользоваться

Методы и статус-коды вы уже знаете. Но «работает» и «спроектировано хорошо» это разные вещи: два разработчика решат одну задачу так, что один API читается с полуслова, а во втором каждый раз лезешь в документацию. В чём разница?

---

## В этом уроке

- **RESTful-принципы**: почему API это набор соглашений, а не только рабочий код
- **Resource naming**: как называть адреса, чтобы они были предсказуемы
- **Versioning**: как менять API и не сломать старых клиентов
- **Swagger / OpenAPI**: контракт API в машинночитаемом виде

---

## Проблема: API работает, но пользоваться им больно

Разработчик написал API для пользователей. Один эндпоинт он назвал `/getUser`, другой `/user/fetch`, третий `/data?action=deleteUser`. Всё технически работает.

Но теперь любой, кто подключается к этому API (мобильное приложение, другой сервис, вы как аналитик), обязан читать документацию к **каждому** адресу: угадать нельзя. Умножьте на сотню эндпоинтов и десяток разработчиков, каждый со своим стилем. Получается хаос, где на изучение API уходит больше времени, чем на саму работу.

Хороший API это не про «работает». Это про **предсказуемость**: зная пару правил, вы понимаете весь API, даже не открывая доки. Эти правила и разбираем.

---

## RESTful-принципы: ресурс это существительное, метод это действие

Вспомните главную идею REST из урока про HTTP: **всё это ресурс (существительное), а метод это действие над ним (глагол)**. Адрес говорит, ЧТО за объект, а метод (`GET`, `POST`, `DELETE`) говорит, что с ним сделать.

```
GET    /users      получить список
POST   /users      создать
GET    /users/5    получить одного
DELETE /users/5    удалить
```

Один ресурс `/users`, а действия задаёт метод. Не надо выдумывать `/getUser`, `/createUser`, `/deleteUser`: глагол уже зашит в метод. В этом вся суть: единый предсказуемый шаблон вместо «у каждого свой велосипед».

## Resource naming: как называть адреса

Соглашения простые, но именно они делают API читаемым. Четыре правила, которые покрывают почти всё.

**1. Существительные, не глаголы.** Действие уже в методе. `POST /orders`, а не `POST /createOrder`.

**2. Множественное число для коллекций.** Коллекция во множественном, конкретный элемент через id:

```
GET /users        коллекция (все пользователи)
GET /users/5      элемент (пользователь с id 5)
```

Так делают Stripe, GitHub, вообще все крупные API. Единообразие: и список, и один объект живут на одном ресурсе.

**3. Вложенность для связей, но неглубоко.** Заказы конкретного пользователя:

```
GET /users/5/orders     заказы пользователя 5
```

Глубже одного уровня лучше не залезать: `/users/5/orders/12/items/3` читается тяжело, такое разбивают на отдельные ресурсы.

**4. Фильтры и сортировка через query, а не новыми путями.** Не плодите адреса под каждый случай:

```
GET /products?category=phones&sort=price
```

Один ресурс `/products`, а «какие именно и в каком порядке» уточняет query. Вспомните из HTTP-урока: path говорит ЧТО за ресурс, query уточняет КАК его отдать.

> ❓ Спроектируйте адрес: «получить отзывы (reviews) товара с id 7». Ресурс, метод, путь.

## Типичная ошибка

9 из 10 новичков тащат глагол в адрес: `GET /getUsers`, `POST /createOrder`, а хуже всего `GET /deleteUser?id=5`. Последнее ломает сразу два правила: удаление через `GET` (а `GET` не должен ничего менять) и глагол в пути.

> ⚠️ Не делайте так: `GET /deleteUser?id=5`. Правильно: `DELETE /users/5`. Действие задаёт метод, адрес это всегда существительное-ресурс.

## Versioning: менять API, не ломая старых клиентов

Проблема, которую чувствуешь только на живом проекте. У вашего API уже есть клиенты: мобильное приложение, партнёрские сервисы. Вы решаете переделать ответ `/users`: переименовать поле, убрать лишнее. И в этот момент **все старые клиенты ломаются**, потому что ждали старый формат.

Нельзя просто «поменять API», когда им кто-то пользуется. Решение: **версионирование**. Новую версию выкладываете на отдельном адресе, а старая продолжает работать параллельно, пока клиенты не переедут.

```
GET /v1/users     старая версия, работает как работала
GET /v2/users     новая версия с изменениями
```

Клиенты на `v1` живут спокойно, новые подключаются к `v2`, а вы переводите старых постепенно, а не в один день.

Когда поднимать версию: только на **ломающих изменениях** (breaking changes), когда старый клиент перестанет понимать ответ. Убрали поле, переименовали, изменили тип: это новая версия. А вот **добавить** новое необязательное поле можно и без новой версии: старые клиенты его просто не заметят.

> ❓ Вы добавляете в ответ `/v1/users` новое поле `lastLogin`, старые поля не трогаете. Нужна ли новая версия `v2`? Почему?

## Swagger / OpenAPI: контракт API в машинном виде

Последний вопрос: как этот API документировать? Написать текстом в Confluence «есть эндпоинт /users, принимает то-то»? Такая дока устаревает в день написания и у каждого своя.

**OpenAPI** это стандарт описания REST API: единый формат, в котором перечислены все эндпоинты, их методы, параметры, форматы запроса и ответа. По сути это тот же **контракт**, что XSD/WSDL для SOAP из прошлого урока, но для REST-мира.

**Swagger** это инструменты вокруг OpenAPI. Главный из них, **Swagger UI**, превращает описание в живую документацию: страницу, где видны все эндпоинты и где запрос можно **отправить прямо из браузера** и увидеть ответ.

> 💡 Вывод для аналитика: OpenAPI/Swagger это ваш единый источник правды по API. Не «где-то в переписке», а один актуальный документ, по которому и разработчик, и тестировщик, и вы смотрите одни и те же эндпоинты. Часто именно аналитик следит, чтобы спецификация не расходилась с реальностью.

## 🧠 Module Check

> 💡 **1.** Своими словами: почему хороший API это про предсказуемость, а не только про «работает»?
> **Ответ:** Если API следует соглашениям (ресурс-существительное + метод-действие, единый шаблон), то, зная пару правил, вы понимаете весь API без документации. Непредсказуемый API заставляет читать доки к каждому адресу, и время уходит на изучение, а не на работу.

> 💡 **2. Spot the bug.** Разработчик сделал такие эндпоинты:
> ```
> GET  /getAllUsers
> POST /user/create
> GET  /deleteUser?id=5
> ```
> Найдите ошибки и перепишите правильно.
> **Ответ:** Глаголы в адресах (действие должно быть в методе) и удаление через `GET` (он не должен ничего менять). Правильно: `GET /users`, `POST /users`, `DELETE /users/5`.

> 💡 **3. Use-case.** У вашего API 200 подключённых клиентов. Нужно переименовать поле в ответе `/orders`. Как выкатить изменение, не сломав их?
> **Ответ:** Через версионирование: выложить новый формат на `/v2/orders`, оставив `/v1/orders` работать как раньше. Старые клиенты сидят на `v1`, новые идут на `v2`, перевод делается постепенно.

> 💡 **4. True / False + объясни.** «Любое изменение в API требует новой версии».
> **Ответ:** False. Новая версия нужна только для **ломающих** изменений (убрали/переименовали поле, сменили тип). Добавление нового необязательного поля версии не требует: старые клиенты его просто игнорируют.

> 💡 **5. Compare.** Чем OpenAPI/Swagger лучше текстовой документации API в Confluence?
> **Ответ:** OpenAPI это машинночитаемый стандарт: один формат, по которому все смотрят одни эндпоинты, из него генерируется живая дока (Swagger UI), где запрос можно тут же отправить. Текстовая дока устаревает, у каждого своя и её нельзя «выполнить».
