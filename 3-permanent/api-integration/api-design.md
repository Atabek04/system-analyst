## Проблема: API работает, но пользоваться им больно

Разработчик написал API для пользователей. Один эндпоинт он назвал `/getUser`, другой `/user/fetch`, третий `/data?action=deleteUser`. Всё технически работает.

Но теперь любой, кто подключается к этому API (мобильное приложение, другой сервис, вы как аналитик), обязан читать документацию к **каждому** адресу: угадать нельзя. Умножьте на сотню эндпоинтов и десяток разработчиков, каждый со своим стилем. Получается хаос, где на изучение API уходит больше времени, чем на саму работу.

Хороший API это не про «работает». Это про **предсказуемость**: зная пару правил, вы понимаете весь API, даже не открывая доки. Эти правила и разбираем.

## RESTful-принципы: ресурс это существительное, метод это действие

Вспомните главную идею REST из урока про HTTP: **всё это ресурс (существительное), а метод это действие над ним (глагол)**. Адрес говорит, ЧТО за объект, а метод (`GET`, `POST`, `DELETE`) говорит, что с ним сделать.

```
GET    /users      получить список
POST   /users      создать
GET    /users/5    получить одного
DELETE /users/5    удалить
```

Один ресурс `/users`, а действия задаёт метод. Не надо выдумывать `/getUser`, `/createUser`, `/deleteUser`: глагол уже зашит в метод. В этом вся суть: единый предсказуемый шаблон вместо «у каждого свой велосипед».

> [!question] Разработчик сделал эндпоинт `POST /createNewUser`. Что здесь лишнее с точки зрения REST и почему?

## Resource naming: как называть адреса

Соглашения простые, но именно они делают API читаемым. Четыре правила, которые покрывают почти всё.

**1. Существительные, не глаголы.** Действие уже в методе. `POST /orders`, а не `POST /createOrder`.

**2. Множественное число для коллекций.** Коллекция во множественном, конкретный элемент через id:

```
GET /users        коллекция (все пользователи)
GET /users/5      элемент (пользователь с id 5)
```

Так делают Stripe, GitHub, вообще все крупные API. Единообразие: и список, и один объект живут на одном ресурсе.

**3. Вложенность для связей, но неглубоко.** Заказы конкретного пользователя:

```
GET /users/5/orders     заказы пользователя 5
```

Глубже одного уровня лучше не залезать: `/users/5/orders/12/items/3` читается тяжело, такое разбивают на отдельные ресурсы.

**4. Фильтры и сортировка через query, а не новыми путями.** Не плодите адреса под каждый случай:

```
GET /products?category=phones&sort=price
```

Один ресурс `/products`, а «какие именно и в каком порядке» уточняет query. Вспомните из HTTP-урока: path говорит ЧТО за ресурс, query уточняет КАК его отдать.

> [!question] Спроектируйте адрес: «получить отзывы (reviews) товара с id 7». Ресурс, метод, путь.

**5. Единый регистр (casing) и не смешивать его.** В адресах (URL) принято `kebab-case`: `/user-profiles`, а не `/userProfiles` или `/user_profiles`. Внутри JSON-тела принято `camelCase`: `{"firstName": "Ivan"}`, хотя часть команд (особенно в госсекторе и на бэкенде под Python) использует `snake_case`: `{"first_name": "Ivan"}`.

Правило не «что лучше», а «что зафиксировано». Смешение стилей внутри одного API (`/user-profiles` отдаёт `{"first_Name": ...}`) сразу выдаёт непродуманный дизайн и раздражает каждого, кто подключается.

## Типичная ошибка

9 из 10 новичков тащат глагол в адрес: `GET /getUsers`, `POST /createOrder`, а хуже всего `GET /deleteUser?id=5`. Последнее ломает сразу два правила: удаление через `GET` (а `GET` не должен ничего менять) и глагол в пути.

> [!warning] Не делайте так: `GET /deleteUser?id=5`. Правильно: `DELETE /users/5`. Действие задаёт метод, адрес это всегда существительное-ресурс.

## Какой статус-код возвращать на каждое действие

Из урока про HTTP вы знаете коды (200, 404, 500). В API-дизайне важно не просто знать коды, а зафиксировать: **какой код на какое действие возвращает именно этот эндпоинт**, чтобы клиент мог полагаться на код, а не парсить текст ответа.

```
POST   /users        успех → 201 Created (плюс адрес нового ресурса в заголовке Location)
GET    /users/5      успех → 200 OK
DELETE /users/5      успех → 204 No Content (удалили, отдавать нечего)
GET    /users/5      не нашли → 404 Not Found
POST   /users        невалидные данные → 400 Bad Request
```

`204` часто забывают: если тело ответа пустое, код должен сказать об этом сам, а не притворяться `200` с пустым JSON.

### Единый формат ошибки

Ошибка это тоже часть контракта. Если один эндпоинт возвращает `{"error": "not found"}`, а другой `{"message": "..."， "code": 404}`, клиенту приходится писать отдельный парсер под каждый. Договоритесь об одной форме на весь API:

```json
{
  "code": "USER_NOT_FOUND",
  "message": "Пользователь с id 5 не найден",
  "details": {}
}
```

`code` для программной обработки (клиент сравнивает строку, а не парсит человеческий текст), `message` для человека в логах, `details` для доп. контекста (например, какое поле не прошло валидацию).

> [!question] Зачем нужен отдельный `code` вроде `USER_NOT_FOUND`, если и так есть HTTP-статус `404`?

## Пагинация, фильтрация, сортировка: как отдавать большие списки

Проблема: `GET /orders` у крупного магазина вернёт миллионы записей одним ответом. Сервер захлебнётся формируя такой JSON, клиент захлебнётся его получая.

**Пагинация** режет список на страницы. Два основных подхода:

```
# Offset-based: проще, но "проседает" при живых данных (кто-то удалил запись, страницы съезжают)
GET /orders?limit=20&offset=40

# Cursor-based: устойчивее, курсор указывает "начни после этой записи"
GET /orders?limit=20&cursor=eyJpZCI6NDB9
```

Offset-based проще объяснить и реализовать, cursor-based выбирают там, где данные часто меняются в реальном времени (лента, список заказов). Ответ обычно несёт метаданные:

```json
{
  "data": [ ... ],
  "pagination": { "total": 5000, "limit": 20, "offset": 40, "hasMore": true }
}
```

**Фильтрация и сортировка** уже знакомы: query-параметры уточняют, какие именно записи и в каком порядке.

```
GET /products?category=phones&minPrice=100&sort=-price
```

`sort=-price` (минус впереди) частое соглашение для "по убыванию", `sort=price` для "по возрастанию". А **field selection** позволяет клиенту попросить только нужные поля, чтобы не тащить лишний JSON:

```
GET /products?fields=id,name,price
```

> [!question] Мобильное приложение с плохим интернетом листает список из 10 000 товаров. Какие два параметра вы добавите в запрос, чтобы он не завис?

## Versioning: менять API, не ломая старых клиентов

Проблема, которую чувствуешь только на живом проекте. У вашего API уже есть клиенты: мобильное приложение, партнёрские сервисы. Вы решаете переделать ответ `/users`: переименовать поле, убрать лишнее. И в этот момент **все старые клиенты ломаются**, потому что ждали старый формат.

Нельзя просто «поменять API», когда им кто-то пользуется. Решение: **версионирование**. Новую версию выкладываете на отдельном адресе, а старая продолжает работать параллельно, пока клиенты не переедут.

```
GET /v1/users     старая версия, работает как работала
GET /v2/users     новая версия с изменениями
```

Клиенты на `v1` живут спокойно, новые подключаются к `v2`, а вы переводите старых постепенно, а не в один день.

Когда поднимать версию: только на **ломающих изменениях** (breaking changes), когда старый клиент перестанет понимать ответ. Убрали поле, переименовали, изменили тип: это новая версия. А вот **добавить** новое необязательное поле можно и без новой версии: старые клиенты его просто не заметят.

> [!question] Вы добавляете в ответ `/v1/users` новое поле `lastLogin`, старые поля не трогаете. Нужна ли новая версия `v2`? Почему?

### Три способа версионировать, не только через URL

`/v1/users` (URL-путь) самый частый способ, потому что версия видна сразу в адресе, и её легко тестировать в браузере. Но есть ещё два:

```
# Через заголовок
GET /users
Accept: application/vnd.myapi.v2+json

# Через query-параметр
GET /users?version=2
```

URL-путь проще для документации и логов, но "загрязняет" адрес ресурса версией (по идее, ресурс `/users` не должен меняться от версии к версии). Заголовок чище с точки зрения REST, но версию не видно в адресной строке, что усложняет отладку. На практике URL-путь выигрывает в большинстве команд именно за простоту, а заголовок чаще встречается в более зрелых enterprise API.

### Как сообщить, что старая версия скоро умрёт

Версию нельзя поддерживать вечно. Когда `v1` пора выключать, клиентов предупреждают заранее, а не отключают в один день:

```
HTTP/1.1 200 OK
Sunset: Sat, 01 Nov 2026 00:00:00 GMT
Deprecation: true
```

Заголовок `Sunset` говорит "после этой даты эндпоинт перестанет работать", `Deprecation` просто помечает "уже устарел, но пока жив". SA обычно фиксирует эту политику (за сколько месяцев предупреждать, куда слать письма партнёрам) в NFR или отдельном документе по интеграции.

## Идемпотентность при повторных запросах и лимиты нагрузки

Из HTTP-урока вы помните: `GET`, `PUT`, `DELETE` идемпотентны, а `POST` нет. Повторный `POST /orders` при плохом интернете создаст **второй** заказ, хотя пользователь просто нажал кнопку дважды из-за зависшего приложения.

Решение: **Idempotency-Key**. Клиент сам генерирует уникальный ключ на попытку операции и присылает его в заголовке, а сервер запоминает: если такой ключ уже обрабатывался, вернуть тот же результат, а не создавать новую запись.

```
POST /orders
Idempotency-Key: 7d8f3a2e-... (сгенерирован клиентом один раз на попытку)
```

Это критично для платежей и госуслуг, где повторный запрос не должен списать деньги или создать вторую заявку дважды.

**Rate limiting** защищает API от перегрузки: сколько запросов клиенту разрешено в единицу времени. Сервер сообщает лимит в заголовках, а не молчит до момента отказа:

```
X-RateLimit-Limit: 100        разрешено 100 запросов
X-RateLimit-Remaining: 42     осталось 42 в текущем окне
X-RateLimit-Reset: 1699999999 когда лимит обнулится
```

Превысили лимит: сервер отвечает `429 Too Many Requests`. SA фиксирует лимиты как часть NFR (Performance/Availability), особенно для партнёрских интеграций.

> [!question] Пользователь на плохом 3G дважды нажал «Оплатить», потому что приложение зависло на 3 секунды. Как Idempotency-Key убережёт от двойного списания?

## Swagger / OpenAPI: контракт API в машинном виде

Последний вопрос: как этот API документировать? Написать текстом в Confluence «есть эндпоинт /users, принимает то-то»? Такая дока устаревает в день написания и у каждого своя.

**OpenAPI** это стандарт описания REST API: единый формат, в котором перечислены все эндпоинты, их методы, параметры, форматы запроса и ответа. По сути это тот же **контракт**, что XSD/WSDL для SOAP из прошлого урока, но для REST-мира.

**Swagger** это инструменты вокруг OpenAPI. Главный из них, **Swagger UI**, превращает описание в живую документацию: страницу, где видны все эндпоинты и где запрос можно **отправить прямо из браузера** и увидеть ответ.

> [!tip] Вывод для аналитика: OpenAPI/Swagger это ваш единый источник правды по API. Не «где-то в переписке», а один актуальный документ, по которому и разработчик, и тестировщик, и вы смотрите одни и те же эндпоинты. Часто именно аналитик следит, чтобы спецификация не расходилась с реальностью.

> [!question] Чем описание API в OpenAPI лучше, чем та же информация текстом на странице Confluence?

### А что если это не REST, а SOAP? WSDL

В госсекторе (и особенно в интеграциях через ШЭП / Smart Bridge, вы это видели в уроке про Data Formats) до сих пор массово живёт **SOAP**, а не REST. У SOAP свой контракт, и называется он не OpenAPI, а **WSDL** (Web Services Description Language).

Идея та же: машиночитаемый документ, где перечислены все операции, входные/выходные параметры, типы данных, адрес сервиса. Разница в формате и эпохе:

| | REST | SOAP |
|---|---|---|
| Контракт | OpenAPI (Swagger) | WSDL |
| Формат контракта | JSON / YAML | XML |
| Формат сообщений | JSON | XML |
| Типы данных | JSON Schema | XSD (уже знаком по Data Formats) |
| Живая документация | Swagger UI, запрос из браузера | обычно нет, тестируют через SoapUI |

Для аналитика это значит одно: если вы работаете с государственным или банковским API на SOAP, ищите не `swagger.json`, а файл `.wsdl`. Читается он тяжелее (весь контракт в XML), но по смыслу это тот же контракт, что и OpenAPI, просто для другого протокола и другой эпохи.

> [!question] Вам прислали интеграцию с госорганом и сказали «вот контракт API». Файл называется `service.wsdl`. Это REST или SOAP, и что вы ожидаете внутри?

### 🔵 Бонус: HATEOAS

Продвинутая идея REST: ответ сервера может нести не только данные, но и **ссылки на связанные действия**, чтобы клиент не хардкодил адреса заранее:

```json
{
  "id": 5,
  "status": "pending",
  "links": {
    "cancel": "/orders/5/cancel",
    "self": "/orders/5"
  }
}
```

На практике большинство REST API этого не делают (это усложняет ответ), но если встретите термин HATEOAS в вакансии или на собеседовании, теперь знаете, о чём речь: "клиент узнаёт, что можно сделать дальше, из самого ответа, а не из отдельной документации".

## 🧠 Module Check

> [!question]- **1.** Своими словами: почему хороший API это про предсказуемость, а не только про «работает»?
> **Ответ:** Если API следует соглашениям (ресурс-существительное + метод-действие, единый шаблон), то, зная пару правил, вы понимаете весь API без документации. Непредсказуемый API заставляет читать доки к каждому адресу, и время уходит на изучение, а не на работу.

> [!question]- **2. Spot the bug.** Разработчик сделал такие эндпоинты:
> ```
> GET  /getAllUsers
> POST /user/create
> GET  /deleteUser?id=5
> ```
> Найдите ошибки и перепишите правильно.
> **Ответ:** Глаголы в адресах (действие должно быть в методе) и удаление через `GET` (он не должен ничего менять). Правильно: `GET /users`, `POST /users`, `DELETE /users/5`.

> [!question]- **3. Use-case.** У вашего API 200 подключённых клиентов. Нужно переименовать поле в ответе `/orders`. Как выкатить изменение, не сломав их?
> **Ответ:** Через версионирование: выложить новый формат на `/v2/orders`, оставив `/v1/orders` работать как раньше. Старые клиенты сидят на `v1`, новые идут на `v2`, перевод делается постепенно.

> [!question]- **4. True / False + объясни.** «Любое изменение в API требует новой версии».
> **Ответ:** False. Новая версия нужна только для **ломающих** изменений (убрали/переименовали поле, сменили тип). Добавление нового необязательного поля версии не требует: старые клиенты его просто игнорируют.

> [!question]- **5. Compare.** Чем OpenAPI/Swagger лучше текстовой документации API в Confluence?
> **Ответ:** OpenAPI это машинночитаемый стандарт: один формат, по которому все смотрят одни эндпоинты, из него генерируется живая дока (Swagger UI), где запрос можно тут же отправить. Текстовая дока устаревает, у каждого своя и её нельзя «выполнить».

> [!question]- **6. Use-case.** Список из 50 000 записей нужно отдать клиенту по частям, и данные при этом постоянно меняются (новые записи добавляются в реальном времени). Offset-based или cursor-based пагинация, и почему?
> **Ответ:** Cursor-based. Offset-based «съезжает»: если между запросами кто-то добавил/удалил запись, страницы сдвигаются и клиент либо видит дубли, либо пропускает записи. Курсор указывает на конкретную запись («начни после этой»), поэтому устойчив к изменениям в реальном времени.

> [!question]- **7. Compare.** Вам передали интеграцию с госорганом, файл называется `service.wsdl`. Чем это отличается от `swagger.json`, который вы видели на прошлых проектах?
> **Ответ:** `.wsdl` это контракт для SOAP (XML-протокол): описывает операции, типы данных (через XSD) и адрес сервиса в формате XML. `swagger.json` (OpenAPI) это контракт для REST в формате JSON/YAML. Оба решают одну задачу (машиночитаемое описание API), но для разных протоколов и разных эпох; SOAP/WSDL до сих пор стандарт в госсекторе и банках.
