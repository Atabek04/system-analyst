### Блок 1: Введение и проблематика

> 	Представьте: пятеро друзей решили создать мобильное приложение. Один начал рисовать дизайн интерфейса, второй - проектировать базу данных, третий - писать API, четвертый - настраивать сервер, пятый - думать над функциями. Что пойдет не так?

**Ответ: Хаос без координации**

- Дизайнер нарисовал экран "Профиль пользователя", а в БД нет таблицы для аватарок
- API возвращает данные в формате XML, а фронтенд ожидает JSON
- Сервер настроен под Node.js, а бэкенд написан на Python
- Все работают над своей частью, но никто не знает, как части соединятся

**Проблема**: Нет общего плана и синхронизации

---

> Почему этот хаос возникает? В чем корень проблемы?

**Ответ: Отсутствие структурированного процесса**

1. **Нет общего видения**: каждый понимает "приложение" по-своему
2. **Нет последовательности**: начали со всех частей одновременно
3. **Нет синхронизации**: никто не знает, что делают остальные
4. **Нет проверки**: интеграция откладывается на потом → поздно обнаруживаются несовместимости

**Вывод**: Нужен процесс, определяющий "что делать" и "в каком порядке"

---

> Можно ли строить дом, начиная с крыши?

**Ответ: Нет, потому что последовательность важна**

**Аналогия со строительством**:

1. **Фундамент** → без него дом рухнет
2. **Стены** → опираются на фундамент
3. **Крыша** → опирается на стены
4. **Отделка** → когда конструкция готова

**То же самое в разработке ПО**:

1. **Планирование** → понять, ЧТО строим
2. **Требования** → детально описать функции
3. **Проектирование** → спроектировать архитектуру
4. **Разработка** → написать код
5. **Тестирование** → проверить работоспособность
6. **Развертывание** → выпустить пользователям
7. **Поддержка** → исправлять баги, улучшать

---

> Что произойдет, если начать кодить сразу, без планирования?

**Ответ: Переделки, потеря времени и денег**

**Реальный пример**:
- Команда сразу начала писать код интернет-магазина
- Через месяц заказчик спрашивает: "А где функция возврата товара?"
- Оказывается, БД не поддерживает статусы возврата
- Нужно переделывать структуру БД, API, интерфейс → 2 недели работы потеряны

**Вывод**: Чем позже обнаруживаешь ошибку, тем дороже её исправлять

**Почему так?** Каскадный эффект изменений:
- Ошибка на этапе **Требований**: исправить 1 документ → 1 час работы аналитика
- Та же ошибка на этапе **Кода**: изменить требования + архитектуру + код + тесты → 2 недели всей команды
- **Во сколько раз дороже?** В 10-100 раз! Потому что нужно переделывать все слои, построенные поверх ошибки

### Что такое SDLC?

> SDLC расшифровывается как Software Development Life Cycle. Что это такое?

**Ответ: Жизненный цикл разработки программного обеспечения**

**Определение**: Структурированный процесс создания ПО от идеи до поддержки

**Цель SDLC**:
- Обеспечить последовательность действий
- Минимизировать риски и ошибки
- Улучшить качество продукта
- Контролировать сроки и бюджет
- Создать артефакты (документацию) для команды

**SDLC отвечает на вопросы**:
1. Какие этапы проходит проект?
2. Кто отвечает за каждый этап?
3. Что создается на каждом этапе?
4. Когда переходить к следующему этапу?

---

> Статистика 2020-х годов: более 50% IT-проектов проваливаются или значительно превышают бюджет. Почему?

**Ответ: Основные причины провалов**

1. **Неправильная интерпретация бизнес-целей**
   - Разработали не то, что нужно заказчику
   - Пример: заказчик хотел "систему учета", а получил "CRM"

2. **Игнорирование обратной связи от клиентов**
   - Не спрашивали пользователей, что им удобно
   - Выпустили продукт, которым никто не хочет пользоваться

3. **Неверный выбор методологии разработки**
   - Использовали Waterfall для проекта с меняющимися требованиями
   - Или наоборот: Agile для проекта с фиксированными требованиями

4. **Отсутствие планирования и контроля**
   - Не оценили сроки и риски
   - Не отслеживали прогресс

**Вывод**: SDLC помогает избежать этих ошибок

---

> Почему провал проекта - это не только потеря денег?

**Ответ: Последствия шире, чем финансы**

**Что теряется при провале проекта**:

1. **Репутация компании** → клиенты теряют доверие
2. **Время на рынке** → конкуренты обгоняют
3. **Мотивация команды** → разработчики выгорают, увольняются
4. **Возможности бизнеса** → упущенная прибыль

**Пример**: Стартап разрабатывал приложение для доставки еды 2 года. За это время на рынок вышли 5 конкурентов. Когда приложение выпустили, рынок уже был занят. Компания закрылась.

**Вывод**: SDLC помогает выпускать продукты вовремя и качественно

### Блок 2: Этапы SDLC

> Фаза 1: Планирование. Что это и зачем нужно?

**Ответ: Фундамент проекта - определяем ЧТО, ЗАЧЕМ, СКОЛЬКО**

**Что такое фаза планирования?**
- Определение целей проекта, границ (scope), сроков, бюджета, ресурсов
- Оценка рисков и реализуемости (feasibility)

**Зачем планировать?**
- Проекты с планированием успешны в **2.5 раза чаще**
- Без планирования: **45% превышение бюджета** в среднем
- С хорошим планированием: **80% проектов сдаются вовремя**

---

> Клиент говорит: "Хочу приложение для записи к врачам". С чего начать планирование?

**Ответ: 3 ключевых вопроса**

**1. Бизнес-цели и scope (границы)**:
   - Зачем нужно приложение? Какую проблему решает?
   - Что входит в проект? (запись к врачам)
   - Что НЕ входит? (оплата услуг, телемедицина)

**2. Ресурсы и сроки**:
   - Бюджет: 50 000$ или 500 000$?
   - Команда: 3 человека или 20?
   - Сроки: 3 месяца или 1 год?

**3. Реализуемость и риски**:
   - Технически возможно? (интеграция с существующей системой больницы)
   - Экономически выгодно? (окупятся ли инвестиции?)
   - Юридически допустимо? (соблюдение закона о медданных)
   - Риски: конкуренты, изменения законов, нехватка специалистов

**Участники фазы**:
- Product Owner / Заказчик
- Business Analyst / System Analyst
- Project Manager
- Технический лидер (оценка технической реализуемости)

**Артефакты**:
- Project Charter (формальное разрешение на проект, цели, границы)
- Feasibility Study (анализ реализуемости: техническая, экономическая, юридическая)
- Risk Register (реестр рисков и стратегий их снижения)
- Project Plan (план выполнения с этапами и вехами)

---

> Мы поняли бизнес-цели. Теперь нужно зафиксировать "что именно система должна делать". Как это сделать?

**Ответ: Фаза 2 - Определение требований (Requirements)**

**Что делаем**:

1. **Собираем функциональные требования**:
   - Пользователь должен видеть свободные слоты врачей
   - Пользователь должен отменить запись за 24 часа
   - Врач должен видеть список пациентов на день

2. **Собираем нефункциональные требования**:
   - Производительность: система должна выдерживать 1000 одновременных пользователей
   - Безопасность: данные пациентов должны быть зашифрованы
   - Доступность: система работает 24/7

3. **Детализируем каждое требование**:
   - Что произойдет, если пользователь попытается записаться на занятый слот?
   - Что если врач заболел - как отменить все записи?

**Участники фазы**:
- Business Analyst / System Analyst (ведущая роль)
- Product Owner
- Stakeholders (врачи, администраторы клиники, пациенты)
- UX/UI дизайнер (для пользовательских требований)

**Артефакты**:
- SRS (Software Requirements Specification) - спецификация требований
- User Stories / Use Cases
- Acceptance Criteria (критерии приемки)

---

> Требования зафиксированы. Теперь нужно решить: как технически это реализовать? Что между архитектором и строителями?

**Ответ: Фаза 3 - Проектирование (Design)**

**Аналогия**: Архитектор рисует чертежи здания. Строители не могут начать, пока нет чертежей.

**Что делаем в Design**:

1. **Архитектура системы**:
   - Какие компоненты будут? (веб-приложение, мобильное приложение, сервер, БД)
   - Как они взаимодействуют? (REST API, WebSocket)
   - Где будет развернуто? (облако AWS, on-premise сервер)

2. **Проектирование базы данных**:
   - Какие таблицы? (Users, Doctors, Appointments)
   - Как связаны? (один врач → много записей)
   - Индексы для производительности

3. **UI/UX дизайн**:
   - Макеты экранов (Figma, Sketch)
   - Пользовательские сценарии (как пациент делает запись за 3 клика)

**Участники фазы**:
- Solution Architect / Software Architect
- Tech Lead
- Senior Developers
- System Analyst (связь между требованиями и дизайном)
- UX/UI Designer

**Артефакты**:
- DDS (Design Document Specification) - документ проектирования
- ERD (Entity-Relationship Diagram) - диаграмма БД
- UML диаграммы (Use Case, Sequence, Class)
- UI/UX макеты (прототипы экранов)

---

> Когда разработчики начинают писать код?

**Ответ: Фаза 4 - Разработка (Development)**

**Важно**: Разработка начинается ПОСЛЕ того, как:
- Требования зафиксированы (SRS готов)
- Архитектура спроектирована (DDS готов)
- Дизайн согласован (макеты утверждены)

**Что делаем**:

1. **Написание кода**:
   - Frontend разработчики пишут интерфейс (React, Vue, Angular)
   - Backend разработчики пишут API (Node.js, Java, Python)
   - Database администраторы создают структуру БД

2. **Следование стандартам**:
   - Code style (как писать код в команде)
   - Naming conventions (как называть переменные)
   - Code review (проверка кода коллегами)

3. **Unit тестирование**:
   - Разработчик пишет тесты для своего кода
   - Проверяет: работает ли функция корректно?

**Участники фазы**:
- Frontend Developers
- Backend Developers
- Mobile Developers (если есть мобильное приложение)
- DevOps Engineer (настройка CI/CD, окружений)

**Артефакты**:
- Исходный код (в Git репозитории)
- Unit тесты
- Документация API (Swagger/OpenAPI)

---

> Код написан. Можно ли сразу отправлять пользователям?

**Ответ: НЕТ! Сначала - Фаза 5: Тестирование**

**Почему баги попадают в продакшн?**
- Разработчики тестируют только "счастливый путь" (когда все идет по плану)
- Не проверяют граничные случаи (что если пользователь ввел пустое имя?)
- Не проверяют интеграцию (как работает фронтенд + бэкенд вместе?)

**Виды тестирования**:

1. **Integration Testing** (интеграционное):
   - Проверяют, как компоненты работают вместе
   - Пример: API корректно сохраняет запись в БД?

2. **System Testing** (системное):
   - Проверяют систему целиком
   - Пример: пользователь может записаться к врачу от начала до конца?

3. **UAT (User Acceptance Testing)** (приемочное):
   - Реальные пользователи (врачи, пациенты) тестируют систему
   - Проверяют: удобно ли? понятно ли?

4. **Performance Testing** (нагрузочное):
   - Выдерживает ли система 1000 пользователей одновременно?

5. **Security Testing** (тестирование безопасности):
   - Можно ли взломать систему? Утекут ли данные?

**Участники фазы**:
- QA Engineers (тестировщики)
- Test Automation Engineers (автоматизация тестов)
- Business Analyst / System Analyst (проведение UAT с пользователями)
- Security Specialists (для security testing)

**Артефакты**:
- Test Cases (тест-кейсы)
- Bug Reports (отчеты об ошибках)
- Test Coverage Report (покрытие тестами)
- UAT Sign-off (подтверждение от пользователей)

---

> Все тесты пройдены, баги исправлены. Куда отправить код, чтобы пользователи увидели приложение?

**Ответ: Фаза 6 - Развертывание (Deployment)**

**Что делаем**:

1. **Подготовка окружения**:
   - Production сервер настроен
   - База данных развернута
   - Сертификаты безопасности установлены (HTTPS)

2. **Деплой кода**:
   - Frontend загружается на веб-сервер
   - Backend запускается на сервере приложений
   - БД миграции выполняются

3. **Проверка после деплоя**:
   - Smoke testing: работают ли основные функции?
   - Мониторинг: нет ли ошибок в логах?

4. **Обучение пользователей**:
   - Документация для врачей и администраторов
   - Видео-инструкции для пациентов
   - Техподдержка готова к вопросам

**Участники фазы**:
- DevOps Engineer (развертывание, автоматизация)
- Release Manager (координация релиза)
- Support Team (техподдержка)
- System Administrator (настройка серверов)

**Артефакты**:
- Release Notes (описание, что нового в релизе)
- Deployment Documentation (инструкция по развертыванию)
- User Manuals (руководства пользователя)
- Rollback Plan (план отката, если что-то пойдет не так)

---

> Приложение выпущено, пользователи работают. Работа разработчиков закончена?

**Ответ: НЕТ! Фаза 7 - Поддержка и сопровождение (Maintenance)**

**Что происходит после релиза**:

1. **Мониторинг системы**:
   - Отслеживание ошибок в логах
   - Проверка производительности (не упала ли скорость?)
   - Доступность сервера (работает ли 24/7?)

2. **Исправление багов**:
   - Пользователи находят ошибки, которые пропустили тестировщики
   - Критичные баги → hotfix (срочное исправление)
   - Некритичные баги → планируются в следующий релиз

3. **Обновления и улучшения**:
   - Пользователи просят новые функции
   - Технологии устаревают → нужно обновлять библиотеки
   - Законы меняются → нужно адаптировать систему

4. **Техническая поддержка**:
   - Ответы на вопросы пользователей
   - Обучение новых пользователей
   - Решение проблем с доступом

**Участники фазы**:
- Support Team (1-я линия: ответы пользователям)
- DevOps (мониторинг, инфраструктура)
- Developers (исправление багов, hotfixes)
- Project Manager (планирование обновлений)

**Артефакты**:
- Incident Reports (отчеты об инцидентах)
- Patch Releases (обновления с исправлениями)
- Change Logs (история изменений)
- Support Tickets (запросы пользователей)

### Проверка понимания (Mid-Lesson Check)

> **Вопрос для размышления**: Назовите 3 этапа SDLC, которые происходят ДО того, как программист напишет первую строку кода.

**Время на размышление**: 30 секунд

**Ответ**:
1. **Планирование и анализ** - понять бизнес-цели, оценить ресурсы
2. **Определение требований** - зафиксировать, ЧТО система должна делать
3. **Проектирование** - спроектировать, КАК технически реализовать

**Почему это важно?**
- Если начать кодить без требований → будешь переделывать
- Если начать кодить без дизайна → архитектура будет хаотичной
- Стоимость исправления ошибки на этапе кода в 10-100 раз дороже, чем на этапе требований

---

> **Вопрос для размышления**: Что происходит ПОСЛЕ написания кода, но ДО того, как пользователи получат доступ к приложению?

**Время на размышление**: 30 секунд

**Ответ**:
1. **Тестирование** - проверка работоспособности, поиск багов
2. **Развертывание** - выпуск на production сервер

**Почему нельзя пропустить тестирование?**
- Баги в production → потеря доверия пользователей
- Критичная ошибка в медицинском приложении → угроза жизни
- Проблемы с безопасностью → утечка данных

### Блок 3: История методологий - Waterfall: миф и реальность

> NASA в 1960-х годах разрабатывала Project Mercury - первый американский пилотируемый космический корабль. Миллионы строк кода, сотни инженеров. Как они работали?

**Ответ: Итеративная разработка с тестированием**

**Реальная история NASA**:

1. **Короткие итерации** - работали циклами по полдня
2. **Тестирование перед кодом** - сначала продумывали тесты, потом писали код
3. **Постоянная проверка** - после каждой итерации запускали симуляцию
4. **Вовлечение заказчика** - астронавты участвовали в разработке, давали обратную связь

**Вывод**: В 1960-х итеративная разработка была НОРМОЙ для критичных проектов

---

> В 1970 году Уинстон Ройс (Winston Royce) написал статью "Managing the Development of Large Software Systems". Он описал последовательную модель: Требования → Дизайн → Код → Тестирование. Он рекомендовал эту модель?

**Ответ: НЕТ! Он ПРЕДУПРЕЖДАЛ против неё**

**Что на самом деле написал Ройс**:

> "Я верю в эту концепцию, но описанная реализация РИСКОВАННА и ПРИГЛАШАЕТ ПРОВАЛ"

**Что Ройс предлагал**:

1. **Итерации** - несколько циклов разработки, а не один проход
2. **Раннее прототипирование** - показать клиенту прототип ДО полной разработки
3. **Вовлечение заказчика** - регулярная обратная связь
4. **Возврат к предыдущим этапам** - если на тестировании нашли ошибку в требованиях, вернуться и исправить

**Шокирующий факт**: Ройс ВООБЩЕ НЕ ИСПОЛЬЗОВАЛ термин "waterfall" (водопад)! Этот термин появился позже в 1976 году в статье Bell & Thayer.

---

> Если Ройс предупреждал против последовательной модели, откуда взялся жесткий Waterfall?

**Ответ: DOD-STD-2167 (1985) - стандарт Министерства обороны США**

**История возникновения жесткого Waterfall**:

1. **1970-1980-е**: Правительство США искало способ контролировать военные IT-проекты
2. **1985**: Министерство обороны выпустило стандарт DOD-STD-2167
3. **Неправильная интерпретация**: Взяли диаграмму из статьи Ройса, проигнорировали его предупреждения
4. **Стандартизация**:
   - Жесткие фазы без возврата назад
   - Обязательная детальная документация на каждом этапе
   - Никаких итераций - только последовательность
   - Переход к следующей фазе только после 100% завершения предыдущей

**Результат**: DOD стандарт распространился на правительственные и корпоративные проекты по всему миру

**Вывод**: "Классический Waterfall" - это результат неправильного понимания статьи Ройса и бюрократизации процесса

---

> Забыли добавить функцию "экспорт в PDF" в документ требований (SRS). Обнаружили это через 6 месяцев на этапе тестирования. Что произойдет в Waterfall?

**Ответ: Дорогостоящие переделки**

**Каскад изменений**:

1. **Требования**: Обновить SRS - добавить требование "экспорт в PDF"
2. **Проектирование**: Изменить архитектуру - добавить библиотеку генерации PDF, спроектировать API
3. **Разработка**: Написать код для генерации PDF, интегрировать в систему
4. **Тестирование**: Написать новые тест-кейсы, протестировать функцию
5. **Документация**: Обновить все документы (DDS, User Manual, Release Notes)

**Стоимость ошибки**:
- Если бы нашли на этапе требований: 1 час работы аналитика
- Нашли на этапе тестирования: 2 недели работы всей команды
- **Во сколько раз дороже?** В 10-100 раз!

**Главная проблема Waterfall**: Клиент видит продукт только в конце → изменения слишком дороги

---

> Система управления ядерным реактором. Требования фиксированы законом, нельзя допустить ни одной ошибки. Какой подход использовать?

**Ответ: Waterfall подходит для этого случая**

**Когда Waterfall работает хорошо**:

1. **Стабильные, неизменяемые требования**
   - Требования определены законом или стандартами
   - Невозможны изменения в процессе разработки
   - Пример: атомная энергетика, авиация, медицинское оборудование

2. **Высоко регулируемые отрасли**
   - Обязательна детальная документация для аудита
   - Каждый шаг должен быть задокументирован
   - Пример: государственные проекты, банки, оборонка

3. **Проекты с фиксированным контрактом**
   - Заказчик хочет знать точные сроки и стоимость заранее
   - Все требования известны и согласованы
   - Пример: контракт на разработку системы учета для госучреждения

4. **Критичность ошибок высокая**
   - Ошибка может стоить жизней или огромных денег
   - Нужна тщательная проверка на каждом этапе
   - Пример: системы управления полетами, медицинские системы диагностики

**Вывод**: Waterfall не "плохой" - он просто подходит для специфических контекстов

### Блок 4: Agile - возврат к истокам

> Статистика 1990-х годов: 70% коммерческих IT-проектов провалились или превысили бюджет в 2-3 раза. Почему жесткий Waterfall (из DOD-STD-2167) не работал?

**Ответ: Waterfall плохо подходит для изменяющихся требований**

**Проблемы индустрии 1990-х**:

1. **Требования меняются - рынок не ждет**
   - Конкуренты выпускают новые функции → ваши требования устарели
   - Пример: Начали разработку сайта. Через полгода появился Instagram. Пользователи хотят "вход через соцсети", но в требованиях этого нет.

2. **Клиенты не знают, что хотят, пока не увидят**
   - В SRS написано "удобный интерфейс", но что это значит?
   - Только увидев прототип, клиент понимает: "Нет, кнопка должна быть слева"

3. **Технологии меняются за время разработки**
   - Планировали делать на Flash. Через год вышел iPhone без поддержки Flash.
   - Приходится переписывать архитектуру

4. **Конкуренты выпускают продукты быстрее**
   - Waterfall проект разрабатывается 2 года
   - Конкуренты за это время выпустили 4 версии продукта и заняли рынок

**Вывод**: Для коммерческих продуктов нужна гибкость

---

> Что делать, если не знаешь все требования заранее? Как работать в условиях неопределенности?

**Ответ: Вернуться к итерациям (как NASA в 1960-х!)**

**Попытки решения в 1980-1990-х**:

1. **Spiral Model (Спиральная модель)** - Barry Boehm, 1986
   - Комбинация Waterfall + итерации
   - Каждая итерация: планирование → анализ рисков → разработка → оценка
   - Фокус на управление рисками

2. **RAD (Rapid Application Development)** - James Martin, 1991
   - Быстрая разработка через прототипирование
   - Использование готовых компонентов
   - Активное вовлечение пользователей

3. **RUP (Rational Unified Process)** - 1996
   - Итеративный процесс с 4 фазами
   - Много церемоний и документации
   - Слишком тяжеловесный для малых проектов

**Проблема**: Нет единого подхода → каждая компания делает по-своему → хаос продолжается

---

> 17 разработчиков встретились на лыжном курорте Snowbird (штат Юта, США) в феврале 2001 года. Что они создали?

**Ответ: Agile Manifesto - манифест гибкой разработки**

**Кто были эти люди?**
- Кент Бек (Kent Beck) - создатель Extreme Programming (XP)
- Джефф Сазерленд (Jeff Sutherland) - сооснователь Scrum
- Мартин Фаулер (Martin Fowler) - эксперт по рефакторингу
- и еще 14 опытных практиков

**Что они сделали?**
- НЕ создали новую методологию
- Создали **МАНИФЕСТ ЦЕННОСТЕЙ** - общие принципы для всех гибких подходов

**4 ключевые ценности Agile**:

1. **Люди и взаимодействие** > процессы и инструменты
2. **Работающий продукт** > исчерпывающая документация
3. **Сотрудничество с заказчиком** > согласование условий контракта
4. **Готовность к изменениям** > следование плану

**Важно**: Это приоритеты, а не отрицание. Документация нужна, но не 300-страничный SRS.

---

> Ценность "Люди и взаимодействие > процессы" означает, что можно работать без процессов и правил?

**Ответ: НЕТ! Agile = дисциплинированная гибкость**

**Что НЕ значит Agile**:

❌ "Делаем что хотим без плана"
❌ "Документация не нужна"
❌ "Никаких процессов"
❌ "Меняем требования каждый день"

**Что ЗНАЧИТ Agile**:

✓ Приоритет на людей, но процессы есть и они важны
✓ Документация нужна, но минимальная и полезная (не ради документации)
✓ План есть, но гибкий (можем адаптировать)
✓ Изменения возможны, но контролируемые (не хаос)

**Пример дисциплины в Agile**:
- **Короткие спринты** (2-4 недели) - фиксированная длительность
- **Ежедневные стендапы** (15 минут) - обязательные, в одно время
- **Ретроспективы** - обязательная рефлексия после спринта
- **Definition of Done** - четкие критерии завершения задачи

**Вывод**: Agile - это не отсутствие дисциплины, а другой тип дисциплины

---

> Как организовать работу по Agile на практике? Манифест дал ценности, но не описал конкретный процесс.

**Ответ: Scrum - популярный Agile фреймворк**

**Scrum предоставляет конкретную структуру**:

**1. Роли**:
- **Product Owner** - определяет приоритеты, что разрабатывать
- **Scrum Master** - следит за процессом, устраняет препятствия
- **Development Team** - разработчики, тестировщики, дизайнеры (3-9 человек)

**2. Артефакты**:
- **Product Backlog** - список всех требований, приоритизированный
- **Sprint Backlog** - задачи на текущий спринт
- **Increment** - рабочий продукт после каждого спринта

**3. Церемонии (события)**:
- **Sprint Planning** - планирование спринта (что будем делать?)
- **Daily Standup** - ежедневная встреча 15 минут (что сделал? что планирую? есть ли препятствия?)
- **Sprint Review** - демонстрация результата заказчику
- **Retrospective** - ретроспектива (что прошло хорошо? что улучшить?)

**4. Спринты**:
- Фиксированная длительность: 2-4 недели
- Результат каждого спринта: рабочий продукт (можно показать клиенту)

**Пример**: Спринт 2 недели. Команда взяла 5 задач из Product Backlog. Через 2 недели выпустили функцию "поиск товаров". Показали клиенту. Клиент попросил добавить фильтры. Это идет в следующий спринт.

---

> В чем разница между Scrum и Kanban? Оба относятся к Agile.

**Ответ: Scrum - спринты, Kanban - непрерывный поток**

**Scrum**:
- **Фиксированные спринты** (2-4 недели)
- **Обязательства на спринт**: команда берет задачи и обещает выполнить за спринт
- **Церемонии**: Planning, Daily, Review, Retro
- **Роли**: PO, SM, Dev Team
- **Когда подходит**: проекты с предсказуемыми релизами, команды 3-9 человек

**Kanban**:
- **Непрерывный поток**: нет фиксированных спринтов, задачи движутся по доске
- **WIP limits (Work In Progress)**: ограничение количества задач "в процессе" → фокус на завершении
- **Гибкость**: можно добавлять задачи в любой момент
- **Меньше церемоний**: нет обязательных Planning/Review
- **Когда подходит**: поддержка, операционные задачи, малые команды, непредсказуемый поток задач

**Пример Kanban**:
- Support команда обрабатывает баги. Каждый день приходит разное количество багов.
- Доска: To Do | In Progress (limit 3) | Testing | Done
- Правило: не берем новую задачу в In Progress, пока там 3 задачи

**Вывод**: Scrum для проектов, Kanban для поддержки и операционной работы

---

> Agile звучит идеально: гибкость, обратная связь, быстрые релизы. Всегда ли он подходит? Может ли Agile провалиться?

**Ответ: Agile не работает без дисциплины и правильного контекста**

**Риски и ошибки Agile**:

1. **Без Scrum Master → хаос**
   - Спринты затягиваются на 6 недель
   - Никто не ходит на Daily Standup
   - Фокус теряется, задачи не завершаются
   - **Пример**: "Мы Agile" = "мы работаем без правил"

2. **Неактивный заказчик → решения без обратной связи**
   - Product Owner не участвует в Sprint Review
   - Команда принимает решения самостоятельно → делают не то, что нужно
   - Через 3 месяца: "Это не то, что я хотел"

3. **Распределенная команда без культуры общения → недопонимание**
   - Разработчики в разных часовых поясах
   - Нет синхронизации → конфликты интеграции
   - Agile требует тесного взаимодействия

4. **Фиксированный контракт + фиксированные требования → Waterfall лучше**
   - Госконтракт с четкими требованиями и сроками
   - Нельзя менять требования → гибкость Agile не нужна
   - Waterfall даст лучшую предсказуемость

**Вывод**: Плохой Agile хуже дисциплинированного Waterfall

### Блок 5: Выбор методологии - практические кейсы

> Как решить: использовать Waterfall или Agile для проекта?

**Ответ: 5 ключевых вопросов для выбора методологии**

**1. Насколько стабильны требования?**
- ✓ Стабильны, известны заранее → Waterfall
- ✗ Меняются, неясны → Agile

**2. Доступен ли заказчик для частой обратной связи?**
- ✓ Готов участвовать в Sprint Review каждые 2 недели → Agile
- ✗ Недоступен, занят, делегировал проект → Waterfall (зафиксировать требования заранее)

**3. Насколько критичны ошибки?**
- ✓ Критичны (авиация, медицина, АЭС) → Waterfall (тщательное тестирование, документация)
- ✗ Некритичны (соцсеть, игра) → Agile (можно быстро исправить)

**4. Какой размер команды?**
- ✓ 3-9 человек → Scrum
- ✓ 1-3 человека → Kanban
- ✗ 50+ человек → Waterfall или масштабируемый Agile (SAFe, LeSS)

**5. Фиксированный контракт или гибкий бюджет?**
- ✓ Фиксированный контракт, известная цена → Waterfall
- ✓ Time & Material, оплата по времени → Agile

**Вывод**: Не существует "лучшей" методологии. Есть "подходящая для контекста"

### Кейс 1: Система управления больницей

> **Сценарий**: Центральная больница, интеграция с государственными системами, требования по закону о медданных (аналог HIPAA), контракт на 3 года, команда 50+ разработчиков. Какая методология?

**Время на размышление**: 1 минута

**Ответ: Waterfall**

**Анализ по 5 вопросам**:

1. **Стабильность требований**: ✓ Фиксированы законом (закон о медданных)
2. **Доступность заказчика**: ✗ Госучреждение, формальные процедуры согласования
3. **Критичность ошибок**: ✓ ОЧЕНЬ высокая (медицинские данные, диагнозы)
4. **Размер команды**: 50+ → слишком много для Scrum
5. **Тип контракта**: Фиксированный на 3 года

**Дополнительные факторы**:
- Интеграция с госсистемами требует согласований
- Обязательна детальная документация для аудита
- Изменения в требованиях требуют согласования с регуляторами → медленно и дорого

**Вывод**: Waterfall с тщательной фазой требований и проектирования

### Кейс 2: Мобильное приложение для фуд-доставки (стартап)

> **Сценарий**: Стартап с 5 разработчиками, тестируют product-market fit (нашли ли подходящий продукт для рынка), требования меняются на основе обратной связи пользователей. Какая методология?

**Время на размышление**: 1 минута

**Ответ: Agile/Scrum**

**Анализ по 5 вопросам**:

1. **Стабильность требований**: ✗ Неясны, нужно экспериментировать
2. **Доступность заказчика**: ✓ Стартап сам заказчик, быстрая обратная связь
3. **Критичность ошибок**: ✗ Можно делать ошибки и учиться
4. **Размер команды**: 5 человек → идеально для Scrum
5. **Тип контракта**: Нет контракта, своя разработка

**Дополнительные факторы**:
- Быстрая обратная связь от пользователей критична
- Конкуренты на рынке → нужна скорость выпуска MVP
- Не знаем, какие функции нужны → A/B тестирование
- Малая команда → легко коммуницировать

**Стратегия**:
- Спринты 2 недели
- Каждый спринт: выпуск новой функции или улучшения
- Метрики: сколько пользователей используют функцию?
- Быстрые эксперименты: попробовали "промокоды" → пользователи не используют → убрали

**Вывод**: Scrum для быстрой итерации и обучения на рынке

### Кейс 3: Обновление legacy системы банка

> **Сценарий**: Банк хочет модернизировать 10-летнюю систему управления счетами. Некоторые модули понятны (переписать как есть), некоторые - новые (улучшить UX для клиентов). Какая методология?

**Время на размышление**: 1 минута

**Ответ: Гибридный подход (Waterfall + Agile)**

**Анализ**:

**Старые модули (переписать как есть)**:
- Требования известны → логика не меняется
- Критично не сломать → нужна тщательная проверка
- **Методология**: Waterfall

**Новые модули (UX улучшения)**:
- Требования неясны → нужна обратная связь от клиентов
- Можно экспериментировать
- **Методология**: Agile

**Стратегия**:

1. **Фаза 1: Миграция данных и критичной логики (Waterfall)**
   - Тщательное планирование
   - Детальная документация архитектуры
   - Полное тестирование перед релизом
   - Срок: 6 месяцев

2. **Фаза 2: Новые UX функции (Agile)**
   - Спринты 2 недели
   - A/B тестирование с клиентами
   - Постепенный выпуск функций
   - Срок: непрерывно после Фазы 1

**Разделение команды**:
- Одна группа: миграция (работают по Waterfall)
- Другая группа: новые фичи (работают по Scrum)

**Вывод**: Не нужно выбирать "или-или". Можно комбинировать подходы

### Кейс 4: E-commerce платформа (средний бизнес)

> **Сценарий**: Компания с 20 разработчиками создает marketplace. Есть базовые требования (каталог товаров, корзина, оплата), но UX и дополнительные функции нужно тестировать с пользователями. Какая методология?

**Время на размышление**: 1 минута

**Ответ: Инкрементная разработка + Agile**

**Стратегия**:

**Инкремент 1: MVP (Minimum Viable Product) - 3 месяца**
- Базовые функции: каталог, корзина, оплата
- Подход: Waterfall для скорости (требования известны)
- Цель: выпустить на рынок как можно быстрее

**Инкремент 2: Улучшения после MVP - Agile**
- Функции на основе обратной связи:
  - Пользователи просят "сравнение товаров" → делаем в спринте 1
  - Метрики показывают: 50% бросают корзину → улучшаем checkout в спринте 2
  - Пользователи хотят "избранное" → делаем в спринте 3

**Разделение команды (20 человек)**:
- 10 разработчиков: MVP (Waterfall)
- 5 разработчиков: улучшения (Agile/Scrum)
- 5 QA + DevOps

**Переход**: После MVP вся команда переходит на Scrum для дальнейших улучшений

**Вывод**: Начать с фиксированных требований, перейти к экспериментам

### Ошибки в выборе методологии - Пример 1

> **Сценарий**: Стартап выбрал Waterfall, потому что "нужна документация для инвесторов". Потратили 8 месяцев на разработку. Выпустили продукт. Конкуренты уже заняли рынок. Что пошло не так?

**Ответ: Неправильный выбор для контекста стартапа**

**Ошибки**:

1. **Неправильная причина выбора Waterfall**
   - "Нужна документация" → можно делать документацию и в Agile
   - Investors Deck (презентация для инвесторов) ≠ 300-страничный SRS

2. **Игнорирование контекста стартапа**
   - Стартапу нужна **скорость**, не тщательная документация
   - Рынок не ждет → конкуренты обгоняют

3. **Неизвестные требования**
   - Стартап не знает, что нужно пользователям → требования меняются
   - Waterfall для неясных требований = потраченное время

**Что нужно было сделать**:
- Agile/Scrum для разработки
- Минимальная документация: User Stories, Product Backlog
- Презентация для инвесторов на основе MVP и метрик пользователей

**Вывод**: Не существует "лучшей" методологии. Есть "подходящая для контекста"

### Ошибки в выборе методологии - Пример 2

> **Сценарий**: Компания перешла на Agile. Через 3 месяца ситуация: спринты по 6 недель, никто не ходит на ретроспективы, требования меняются каждый день без приоритизации. Это Agile?

**Ответ: Это не Agile, это хаос**

**Признаки "плохого Agile"**:

1. **Спринты по 6 недель**
   - Agile требует коротких спринтов (2-4 недели)
   - 6 недель → теряется фокус, слишком долго до обратной связи

2. **Никто не ходит на ретроспективы**
   - Ретроспектива = ключевая церемония для улучшения процесса
   - Без ретро → не учитесь на ошибках

3. **Требования меняются каждый день**
   - Agile ≠ "меняем требования когда хотим"
   - Должна быть стабильность внутри спринта
   - Изменения обсуждаются на Sprint Planning

4. **Нет приоритизации**
   - Без Product Owner → хаос в требованиях
   - Команда не знает, что важнее

**Что не хватает**:
- Scrum Master для дисциплины процесса
- Product Owner для приоритизации
- Commitment команды на процесс

**Вывод**: "Мы Agile" ≠ "мы работаем без правил". Плохой Agile хуже дисциплинированного Waterfall

### Блок 6: Итоговая проверка понимания

> **Комплексный кейс для анализа**
>
> Государственная больница хочет создать систему онлайн-записи пациентов.
>
> **Требования**:
> - Интеграция с существующей системой электронных медкарт (стабильный API)
> - Мобильное приложение для пациентов (UX нужно тестировать с врачами и пациентами)
> - Соблюдение закона о защите медицинских данных
> - Команда: 15 разработчиков (5 backend, 5 frontend/mobile, 5 QA/DevOps)
> - Срок: 12 месяцев
> - Бюджет: фиксированный
>
> **Задание студентам (5 минут на размышление и обсуждение)**:
>
> 1. Какую методологию выбрать?
> 2. Через какие фазы SDLC пройдет проект?
> 3. Кто будет участвовать на каждой фазе?

**Время на размышление и обсуждение**: 5 минут

---

### Ответ на комплексный кейс

**1. Выбор методологии: Гибридный подход**

**Backend интеграция → Waterfall**:
- Интеграция с медкартами: требования ясны (API известен)
- Критично: ошибка в медданных недопустима
- Закон о медданных: обязательна документация

**Frontend мобильное приложение → Agile/Scrum**:
- UX неизвестен → нужно тестировать с пользователями
- Спринты 2 недели с демо врачам и пациентам
- Быстрые итерации для улучшения интерфейса

---

**2. Фазы SDLC (12 месяцев)**

**Фаза 1: Планирование (1 месяц)**
- Анализ бизнес-целей больницы
- Оценка рисков (интеграция, закон)
- Планирование ресурсов

**Участники**:
- Product Owner (представитель больницы)
- Project Manager
- System Analyst
- Tech Lead

**Артефакты**:
- Project Charter
- Risk Register
- Feasibility Study

---

**Фаза 2: Определение требований (1.5 месяца)**

**Для backend интеграции**:
- Детальная спецификация API интеграции
- Требования по безопасности данных
- Соответствие закону о медданных

**Для мобильного приложения**:
- User Stories для врачей и пациентов
- Базовые пользовательские сценарии
- Нефункциональные требования (производительность)

**Участники**:
- System Analyst (ведущая роль)
- Product Owner
- Stakeholders: врачи, администраторы клиники, пациенты
- UX/UI дизайнер
- Security Specialist (для требований безопасности)

**Артефакты**:
- SRS для backend интеграции
- Product Backlog для мобильного приложения
- Use Cases
- Security Requirements

---

**Фаза 3: Проектирование (1.5 месяца)**

**Архитектура системы**:
- Проектирование интеграции с медкартами
- Архитектура мобильного приложения (REST API)
- Проектирование БД для записей
- Безопасность: шифрование, аутентификация

**UI/UX дизайн**:
- Макеты мобильного приложения (Figma)
- Прототипы для тестирования с пользователями

**Участники**:
- Solution Architect
- Tech Lead
- Senior Backend Developers
- Senior Mobile Developers
- System Analyst (связь требований и дизайна)
- UX/UI Designer
- Database Administrator

**Артефакты**:
- DDS (Design Document Specification)
- ERD (диаграмма базы данных)
- API спецификация (Swagger/OpenAPI)
- UI/UX макеты
- Security Architecture Document

---

**Фаза 4: Разработка (6 месяцев)**

**Параллельная работа двух команд**:

**Команда 1: Backend интеграция (Waterfall)**
- Разработка API для записи к врачам
- Интеграция с системой медкарт
- Реализация безопасности (шифрование, RBAC)
- Месяцы 1-6: последовательная разработка с тестированием

**Команда 2: Mobile приложение (Scrum)**
- Спринты по 2 недели (12 спринтов за 6 месяцев)
- Каждый спринт: новая функция или улучшение UX
- Sprint Review с врачами и пациентами
- Итеративное улучшение интерфейса

**Участники**:
- 5 Backend Developers (команда 1)
- 5 Frontend/Mobile Developers (команда 2)
- DevOps Engineer (настройка CI/CD, окружений)
- Scrum Master для команды 2

**Артефакты**:
- Исходный код (Git репозиторий)
- Unit тесты
- API документация
- Инкременты мобильного приложения (каждые 2 недели)

---

**Фаза 5: Тестирование (1.5 месяца)**

**Интеграционное тестирование**:
- Проверка интеграции мобильного приложения с backend
- Проверка интеграции с системой медкарт

**System Testing**:
- End-to-end тестирование: пациент записывается → врач видит запись

**UAT (User Acceptance Testing)**:
- Врачи тестируют функции управления расписанием
- Пациенты тестируют процесс записи
- Администраторы тестируют отчеты

**Performance Testing**:
- Нагрузочное тестирование: 1000 одновременных пользователей

**Security Testing**:
- Проверка соответствия закону о медданных
- Тестирование на проникновение (penetration testing)

**Участники**:
- QA Engineers (5 человек)
- System Analyst (UAT с пользователями)
- Security Specialist (security testing)
- Врачи, пациенты (UAT)

**Артефакты**:
- Test Cases
- Bug Reports
- Test Coverage Report
- UAT Sign-off
- Security Audit Report

---

**Фаза 6: Развертывание (0.5 месяца)**

**Подготовка production окружения**:
- Настройка серверов больницы
- Развертывание БД с шифрованием
- Публикация мобильного приложения в App Store / Google Play

**Миграция данных**:
- Импорт расписаний врачей
- Тестовые записи для проверки

**Обучение пользователей**:
- Тренинг для врачей и администраторов
- Видео-инструкции для пациентов

**Участники**:
- DevOps Engineer
- Release Manager
- System Administrator
- Support Team

**Артефакты**:
- Release Notes
- Deployment Documentation
- User Manuals (для врачей, пациентов, администраторов)
- Rollback Plan

---

**Фаза 7: Поддержка (после релиза)**

**Мониторинг**:
- Отслеживание ошибок в приложении
- Проверка производительности сервера
- Мониторинг безопасности

**Исправление багов**:
- Критичные баги → hotfix (срочное исправление)
- Некритичные баги → планируются в обновление

**Обновления**:
- Новые функции на основе обратной связи
- Обновление библиотек для безопасности

**Участники**:
- Support Team (1-я линия поддержки)
- DevOps (мониторинг инфраструктуры)
- Developers (hotfixes, обновления)
- Project Manager (планирование улучшений)

**Артефакты**:
- Incident Reports
- Patch Releases
- Change Logs
- Support Tickets

---

**3. Ключевые особенности проекта**

**Параллельная работа команд**:
- Backend команда: Waterfall (стабильные требования)
- Mobile команда: Scrum (итеративный UX дизайн)
- Синхронизация через общий API

**Управление рисками**:
- Критичность медданных → тщательное security testing

### Итоговые выводы

**Ключевые инсайты**:

1. **SDLC - структурированный процесс** от идеи до поддержки
   - 7 фаз: Планирование → Требования → Проектирование → Разработка → Тестирование → Развертывание → Поддержка
   - Каждая фаза создает артефакты
   - Определенные участники на каждой фазе

2. **Waterfall был неправильно понят**
   - Royce предупреждал против последовательности
   - DOD-STD-2167 (1985) стандартизировал неверную интерпретацию
   - Waterfall подходит для стабильных требований и высоко регулируемых отраслей

3. **Agile - возврат к итерациям (как NASA в 1960-х)**
   - Не революция, а формализация итеративных принципов
   - Agile Manifesto (2001): 4 ценности
   - Agile требует дисциплины (Scrum церемонии, роли)

4. **Нет "лучшей" методологии**
   - Есть подходящая для контекста
   - 5 вопросов для выбора: стабильность требований, доступность заказчика, критичность ошибок, размер команды, тип контракта
   - Можно комбинировать: гибридный подход

5. **System Analyst - ключевая роль**
   - Фазы 1-3: Планирование, Требования, Проектирование
   - Связующее звено между бизнесом и технической командой
   - Ответственность за SRS, участие в DDS, проведение UAT

**Что дальше**:
- Практические навыки по Scrum
- Глубокое изучение Requirements Engineering
- Моделирование процессов (BPMN, UML)
