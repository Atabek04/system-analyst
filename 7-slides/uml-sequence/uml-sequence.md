# Sequence Diagram

# Где мы в карте диаграмм

| Диаграмма    | Отвечает на вопрос                      |
| ------------ | --------------------------------------- |
| Use Case     | **ЧТО** система делает для пользователя |
| **Sequence** | **КАК** участники общаются между собой  |
| Class        | **ИЗ ЧЕГО** состоит система изнутри     |

**Sequence Diagram** — главный язык SA в разговоре с разработчиками.

> Use Case — это договор с бизнесом. Sequence — это техзадание для команды.

# Sequence Diagram = порядок сообщений во времени

Ось **Y** — это время. Сверху вниз. Каждое сообщение — стрелка между участниками.

![bg right:45%](img/seq-cafe.png)

Вы только что описали это словами:
- **Клиент → Официант** → сделал заказ
- **Официант → Бариста** → передал заказ
- **Бариста → Официант** → готово
- **Официант → Клиент** → подал кофе

> Sequence Diagram — та же история, но строгая и однозначная.

# У нас есть BPMN. Зачем ещё Sequence?

**Разница:**
- BPMN читает **бизнес** — Sequence читает **разработчик**
- BPMN: "оплатить заказ" — Sequence: `POST /payments → 200 {txId}` или `402`
- BPMN не показывает sync/async и кто ждёт — Sequence показывает

**Порядок:** BPMN → Use Case → Sequence Diagram

**Нужны ли оба?** Не всегда. Для простых фич хватает Sequence. Оба — когда процесс сложный и его надо показать и бизнесу, и команде.

> BPMN — договор с бизнесом. Sequence — техзадание для разработчика.

<!--
Teacher Notes:
- Спроси: "Может ли разработчик написать API только по BPMN?" → Нет. Не знает метод, формат, коды ошибок.
- Спроси: "А зачем тогда BPMN если есть Sequence?" → Бизнес не читает Sequence. BPMN — общий язык с заказчиком.
- ~3 мин

# Participant — участник диаграммы

**Participant** — любой, кто отправляет или получает сообщение.

- Отображается как **прямоугольник** сверху
- Типы: **Actor** (человек), **System** (сервис), **Database** (хранилище)
- Максимум **5-7 Participant** на одной диаграмме — иначе нечитаемо

**Пример для Wolt:**

![](img/seq-wolt-participants.png)

> Если участников больше 7 — разбей на несколько диаграмм по сценариям.

<!--
Teacher Notes:
- Покажи: Participant живёт сверху. От него вниз идёт линия — это Lifeline.
- Про типы: Actor — человечек, System — прямоугольник, Database — цилиндр. В простых диаграммах все изображаются прямоугольниками.
- ~2 мин
-->

---

# Lifeline — "жизнь" участника

**Lifeline** — пунктирная вертикальная линия, которая идёт вниз от каждого Participant.

- Показывает, что участник **существует** в процессе
- Сверху вниз = ход времени
- Сообщения "висят" на этой линии

![](img/seq-lifeline.png)

> Lifeline — это просто "ось времени" конкретного участника.

<!--
Teacher Notes:
- Простой слайд — не затягивай. Lifeline — фундамент, но интуитивно понятен.
- Акцентируй: пунктир, вертикально, вниз = время.
- ~1 мин
-->

---

# Activation Box — участник занят

**Activation Box** — прямоугольник на Lifeline. Показывает: участник сейчас **обрабатывает запрос**.

- Узкий прямоугольник поверх пунктира
- Начинается, когда получено сообщение
- Заканчивается, когда отправлен ответ
- Показывает **КОГДА** участник работает, а когда просто ждёт

![](img/seq-activation.png)

> Без Activation Box непонятно, сколько времени система тратит на обработку.

<!--
Teacher Notes:

- ~2 мин

# Типы сообщений

| Тип                   | Mermaid | Стрелка                       | Смысл                     |
| --------------------- | ------- | ----------------------------- | ------------------------- |
| **Синхронный вызов**  | `->>`   | сплошная, закрытый наконечник | Отправил и **жду** ответа |
| **Асинхронный вызов** | `-)`    | сплошная, открытый наконечник | Отправил и **не жду**     |
| **Ответ**             | `-->>`  | пунктир, закрытый наконечник  | Вернул результат          |
| **Self-call**         | петля   | стрелка на себя               | Сам себе вызвал метод     |

![bg right:40%](img/seq-sync-async.png)

**Пример:**
- Wolt App ->> Order Service: создать заказ *(sync)*
- Order Service -) Ресторан: уведомить о заказе *(async)*

<!--
Teacher Notes:
- Самое важное: sync vs async. Sync — ты стоишь у кассы и ждёшь сдачу. Async — ты заказал пиццу и пошёл заниматься своим делом.
- Ответ всегда пунктиром — это правило, которое часто нарушают.
- ~3 мин
-->

# Self-call — когда система вызывает себя

![bg right:55%](img/seq-self-call.png)

**Self-call** — сервис вызывает **свою внутреннюю логику** перед тем как идти дальше.

Когда это нужно:
- **Вычисление** — `calculateTotal()` перед отправкой в оплату
- **Валидация** — `validateStock()` перед резервированием
- **Трансформация** — `formatData()` перед сохранением в БД

> Показывай self-call только когда эта логика важна для понимания сценария. Не засоряй диаграмму внутренними деталями реализации.

<!--
Teacher Notes:
- Частая ошибка: рисуют self-call для каждого внутреннего метода — диаграмма превращается в код. Правило: self-call = бизнес-значимый шаг, не реализация.
- Спроси: "Нужно ли рисовать self-call для каждого SQL запроса?" → Нет. Это детали реализации, не взаимодействие систем.
- ~2 мин
-->

# Sync vs Async — запомни навсегда

**Sync** — ты звонишь в поддержку и **держишь трубку**. Ничего не делаешь пока не ответят.

**Async** — ты оставляешь заявку и **кладёшь трубку**. Тебе перезвонят — а пока занимаешься своим делом.

| Ситуация                    | Тип       | Почему                                  |
| --------------------------- | --------- | --------------------------------------- |
| Оплата заказа               | **sync**  | Нельзя отдать товар без подтверждения   |
| Отправить email-уведомление | **async** | Письмо дойдёт само, не надо ждать       |
| Проверить пароль в БД       | **sync**  | Нельзя пустить пользователя без ответа  |
| Уведомить курьера           | **async** | Можно продолжить — курьер получит позже |

> Правило: без ответа нельзя двигаться дальше — **sync**. Можно продолжить — **async**.

<!--

# Combined Fragments — управляющие блоки

| Fragment | Аналог в коде   | Смысл                         |
| -------- | --------------- | ----------------------------- |
| **alt**  | `if / else`     | Условие — один из вариантов   |
| **loop** | `for / while`   | Повторение пока условие верно |
| **opt**  | `if` (без else) | Необязательный блок           |
| **ref**  | вызов функции   | Ссылка на другую диаграмму    |

Каждый блок — рамка с ключевым словом (`alt`, `loop`, `opt`) в углу, которая оборачивает группу сообщений.

> Combined Fragment = блок кода, но на диаграмме.

- ~2 мин

# alt — условие (если / иначе)

Авторизация: верный пароль → токен, неверный → ошибка.

![bg right:45%](img/seq-login-full.png)

- Рамка `alt` делит сценарий на варианты
- Каждый вариант — guard condition в `[ ]`
- Выполняется **только один** из них
- Минимум **2 ветки** — иначе используй `opt`

> alt — всегда минимум 2 ветки. Если else нет — используй opt.

<!--
Teacher Notes:
- Студенты спрашивают: "Можно alt без else?" — технически да, но семантически это opt. Правило: alt = всегда есть альтернатива. Без else → opt.
- Можно несколько else: alt [верный] / else [неверный, попытки < 3] / else [неверный, попытки = 3].
- ~3 мин
-->

---

# loop — повторение пока условие верно

![bg right:50%](img/seq-loop.png)

**loop** — как `while` в коде. Блок повторяется пока guard condition выполняется.

Когда выходим из loop — аккаунт блокируется.

> Реальный пример: retry при таймауте API — повторяй запрос пока нет ответа или не исчерпан лимит.

<!--
Teacher Notes:
- Спроси: "Что происходит после выхода из loop?" — выполняется следующий шаг диаграммы.
- Типичная ошибка: рисуют loop бесконечным, без условия выхода.
- ~2 мин
-->

---

# opt — необязательный блок

![bg right:50%](img/seq-opt.png)

**opt** — как `if` без `else`. Блок либо выполняется, либо полностью пропускается.

Чем отличается от alt:
- `opt` — **0 или 1** выполнение, нет альтернативы
- `alt` — **ровно 1** из нескольких веток всегда выполнится

> Используй opt когда действие необязательное и нет альтернативного пути.

<!--
Teacher Notes:
- Спроси: "Когда бы вы использовали opt, а не alt?" → Когда нет else-ветки — просто пропустить блок.
- Частая ошибка: рисуют alt с одной веткой вместо opt.
- ~2 мин
-->

---

# ref — ссылка на другую диаграмму

![bg right:50%](img/seq-ref.png)

Когда сценарий слишком большой — разбей на части. **ref** говорит: "здесь смотри другую диаграмму".

**Когда использовать ref:**
- Процесс оплаты повторяется в нескольких сценариях
- Авторизация вызывается из каждого flow
- Диаграмма стала больше 7 участников

> ref = как Sub-process в BPMN. Не копируй — ссылайся.

<!--
Teacher Notes:
- Аналог Sub-process в BPMN. Студенты уже знают — дай связь.
- Практическое правило: если видишь одинаковый блок на двух диаграммах — выноси в ref.
- ~2 мин
-->

# Полный пример: заказ в интернет-магазине

![bg right:50%](img/seq-order-flow.png)

**Участники:** Пользователь, Магазин, Payment Service, Courier Service

- Пользователь → Магазин: оформить заказ *(sync)*
- Магазин → Payment Service: списать деньги *(sync, ждём)*
- Payment Service → Магазин: успех *(ответ)*
- Магазин -->> Courier Service: передать в доставку *(async, не ждём)*
- Магазин → Пользователь: заказ принят *(ответ)*

> Sync к оплате — нельзя идти дальше без подтверждения. Async к курьеру — не нужно ждать.

<!--
Teacher Notes:
- Это ключевой пример — разбери каждую стрелку. Почему sync, почему async.
- Спроси: "Что будет если оплата async? Магазин отдаст заказ не зная, прошла ли оплата."
- ~3 мин
-->

# Тот же пример — в Mermaid

Скопируй в Notion, GitHub, Confluence — работает без установки.

```
sequenceDiagram
    actor User as Пользователь
    participant Shop as Магазин
    participant Pay as Payment Service
    participant Courier as Courier Service

    User->>Shop: оформить заказ
    activate Shop

    Shop->>Pay: списать деньги
    activate Pay
    Pay-->>Shop: успех
    deactivate Pay

    Shop-)Courier: передать в доставку

    Shop-->>User: заказ принят
    deactivate Shop
```

`->>` — sync, `--)` — async (открытая стрелка), `-->>` — ответ

# Типичные ошибки — часть 1

**Ошибка 1: ответ нарисован сплошной стрелкой**

```
Auth Service → Client: токен   ← НЕВЕРНО (сплошная)
Auth Service --> Client: токен ← ВЕРНО (пунктир)
```

**Ошибка 2: нет Activation Box**

Без него непонятно, когда система обрабатывает запрос, а когда просто ждёт.
Теряется информация о времени обработки.

> Ответ — всегда пунктиром. Activation Box — всегда при обработке.

<!--
Teacher Notes:
- Эти две ошибки встречаются в 80% работ. Проговори их два раза.

# Плохая vs Хорошая диаграмма

**❌ Плохо** — слишком детально, только happy path:
```
API → DB: SELECT * FROM users WHERE email = ?
DB → API: ResultSet row(id=42, email=..., hash=...)
API → API: bcrypt.compare(password, hash)   ← самовызов
API → Client: 200 OK {"token": "eyJ..."}
```

**✓ Хорошо** — уровень систем, alt для ошибок:
```
Client->>API: войти (email, пароль)
API->>DB: проверить пользователя
DB-->>API: результат

alt [пароль верный]
  API-->>Client: токен
else [пароль неверный]
  API-->>Client: 401 Неверные данные
end
```

> SA не пишет код на диаграмме. SA описывает контракт между системами.

# Типичные ошибки — часть 2

**Ошибка 3: слишком детально**

На диаграмме видны SQL-запросы, имена колонок, внутренние методы БД.
Sequence Diagram — про взаимодействие систем, не про реализацию внутри.

**Ошибка 4: только happy path**

Нет `alt` с ошибкой, нет сценария "что если платёж не прошёл". Бизнес и разработчики не поймут, как система ведёт себя при сбоях.

# Чек-лист хорошей Sequence Diagram

- Не более **5-7 Participant** — иначе нечитаемо
- Все **ответные стрелки** — пунктиром
- Есть **Activation Box** у активных участников
- Есть **alt** для error case — не только happy path
- Каждое сообщение **названо** — не просто стрелка
- Уровень детализации — **между системами**, не внутри них
- Диаграмма **соответствует Use Case** — один сценарий, одна диаграмма

> Если коллега-разработчик понял диаграмму без объяснений — она хорошая.

# Итого

> **Sequence Diagram** — язык взаимодействия между системами.

- SA рисует → разработчик читает → они говорят на одном языке
- Ось Y = время. Сверху вниз.
- **Participant** → **Lifeline** → **Activation Box** → **Messages**
- `alt` / `loop` / `opt` — управляющие блоки для условий и повторений
- Всегда показывай и happy path, и error case

> Хорошая Sequence Diagram не требует объяснений. Она читается как история.
