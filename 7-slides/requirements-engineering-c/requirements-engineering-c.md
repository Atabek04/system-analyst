# Зачем приоритизировать?

**Реальность проектов:**
- Время всегда ограничено
- Бюджет всегда ограничен
- Хочется больше чем можем сделать

**Приоритизация помогает:**
- Делать сначала самое ценное
- Говорить "нет" без обид (есть метод)
- Выпустить продукт быстрее

**Без приоритизации:**
- Делаем всё подряд → ничего не доделываем
- Релиз откладывается бесконечно

---

# MoSCoW — Метод приоритизации

**MoSCoW** — разбивка требований на 4 категории:

- **M — Must have**: без этого продукт не работает
- **S — Should have**: важно, но можно отложить
- **C — Could have**: приятно иметь, если время есть
- **W — Won't have**: хорошая идея, но не сейчас

**Правило:** Must have ≤ 60% всех требований

<!--
Teacher Notes:
Если всё Must — значит не приоритизировали. Настоящий Must — это то без чего продукт НЕ РАБОТАЕТ.
-->

---

# MoSCoW — Пример

**Интернет-магазин одежды:**

| Категория | Требования |
|-----------|------------|
| **Must** | Каталог, Корзина, Оформление заказа, Оплата |
| **Should** | Избранное, Фильтры, История заказов, Отзывы |
| **Could** | Рекомендации, Чат поддержки, Программа лояльности |
| **Won't** | AR примерка, AI стилист, Instagram Shopping |

**Must** — без этого нельзя купить
**Should** — улучшает опыт
**Could** — приятные фишки
**Won't** — версия 2.0

---

# Kano Model — Основы

**Kano Model** — классификация по влиянию на удовлетворённость

**3 типа требований:**

| Тип | Нет | Есть | Пример |
|-----|-----|------|--------|
| **Must-be (базовые)** | Очень плохо | Нейтрально | Тормоза в машине |
| **Performance (линейные)** | Хуже | Чем больше → тем лучше | Скорость доставки |
| **Attractive (восторг)** | Нормально | WOW! | Бесплатный десерт в ресторане |

<!--
VISUAL: График Kano — оси "Реализация" и "Удовлетворённость"
-->

---

# Kano — Примеры

| Тип | Требование | Объяснение |
|-----|------------|------------|
| **Must-be** | Положить в корзину и оплатить | Без этого не магазин |
| **Must-be** | Сайт работает на телефоне | Базовое ожидание 2026 |
| **Performance** | Скорость загрузки | Быстрее → лучше |
| **Performance** | Количество товаров | Больше выбор → лучше |
| **Attractive** | AR примерка одежды | WOW-эффект |
| **Attractive** | Доставка за 2 часа | Неожиданно круто! |

<!--
Teacher Notes:
Must-be не создают преимущество (у всех есть), но без них продукт умрёт. Attractive создают преимущество.
-->

---

# MoSCoW vs Kano

| MoSCoW | Kano | Логика |
|--------|------|--------|
| Must have | Must-be + критичные Performance | Без этого не работает |
| Should have | Performance | Улучшает продукт |
| Could have | Attractive | WOW-фичи |
| Won't have | Любые отложенные | Нет времени/бюджета |

**Вывод:**
- MoSCoW — про КОГДА делать
- Kano — про КАК влияет на пользователя

# MVP — Определение

**MVP — Minimum Viable Product** (минимально жизнеспособный продукт)

**Что это:**
- Версия с минимальным набором функций
- Но минимум УЖЕ решает проблему
- Цель: выпустить быстро, получить обратную связь

**Ключевые принципы:**
- **Minimum** — только необходимое
- **Viable** — работает и даёт ценность
- **Product** — реальный продукт, не макет

---

# MVP — Правильное понимание

**НЕПРАВИЛЬНО:**
```
Колесо → Шасси → Машина без крыши → Машина
```
*До финала пользователь НЕ МОЖЕТ ЕХАТЬ*

**ПРАВИЛЬНО:**
```
Скейтборд ✓ → Самокат ✓ → Велосипед ✓ → Мотоцикл ✓ → Машина ✓
```
*На КАЖДОЙ итерации можно ехать!*

<!--
Teacher Notes:
MVP — не "половина продукта", а "простой, но рабочий продукт". После каждой итерации получаешь обратную связь.

VISUAL: Два ряда — "плохой" (части машины) и "хороший" (скейт → машина)
-->

# MVP и MoSCoW

**Как определить MVP?**

**Простое правило:** MVP = Must have requirements

**Процесс:**
1. Собрали все User Stories
2. Приоритизировали по MoSCoW
3. Взяли только Must have
4. Это и есть MVP

**Пример:**
- **MVP:** Каталог + Корзина + Заказ + Оплата
- **v2.0:** + Избранное + Фильтры + Отзывы
- **v3.0:** + Рекомендации + Чат + Лояльность

---

# MVP — Реальные примеры

| Компания | Первый MVP | Сейчас |
|----------|-----------|--------|
| **Airbnb** | Фото 3 матрасов | Миллионы объектов |
| **Dropbox** | Видео-демо (не продукт!) | Облако для миллиардов |
| **Uber** | Только SF, только премиум | Глобальное такси |
| **Instagram** | Только фото + фильтры | Stories, Reels, шопинг |

> Все начинали с простого, но рабочего решения

# Scope Creep — Определение

**Scope Creep** — неконтролируемое разрастание требований

**Признаки:**
- Постоянно новые "маленькие" задачи
- "А давайте ещё это, это быстро!"
- Сроки не сдвигаются, работы больше

**Почему опасно:**
- Сроки срываются
- Бюджет выходит за рамки
- Качество падает
- Команда выгорает

---

# Почему Scope Creep происходит?

1. **"Это же мелочь!"**
   - 10 мелочей = большая задача

2. **Нет baseline**
   - Не зафиксировали ЧТО делаем

3. **Боимся сказать "нет"**
   - Соглашаемся на всё

4. **Новые идеи в процессе**
   - "О, а можно ещё так?"

5. **Плохая коммуникация**
   - Разработчик согласился без менеджера

---

# Как предотвратить

1. **Baseline Requirements** — зафиксировать scope
2. **Change Request Process** — формальная процедура
3. **"Да, но"** — "Можем, но +2 недели"
4. **Trade-offs** — "Фильтры или личный кабинет?"
5. **Регулярные встречи** — напоминать scope

<!--
MEME: Scope Creep — снежок катится с горы и становится огромным
-->

---

# Change Request Process

**Change Request (CR)** — формальный процесс изменений

**Шаги:**
1. **Заявка** — ЧТО хочет и ЗАЧЕМ
2. **Оценка** — время, деньги, риски
3. **Решение** — добавить или отложить
4. **Документирование** — обновить baseline

**Пример:**
```
ID: CR-001
Что: Фильтр по размеру
Зачем: 60% ищут по размеру (аналитика)
Оценка: 3 дня разработки + 1 тест
Решение: Одобрено, +4 дня к дедлайну
```

# CJM — Customer Journey Map

**CJM** — карта пути клиента через продукт

**Что показывает:**
- Все этапы взаимодействия
- Действия на каждом этапе
- Touchpoints — где "касается" бренда
- Эмоции (позитив/негатив)
- Pain Points — проблемы

**Зачем SA:**
- Найти где улучшить
- Видеть полную картину
- Приоритизировать боли

---

# Компоненты CJM

| Компонент | Что это | Пример |
|-----------|---------|--------|
| **Этапы (Stages)** | Фазы пути клиента | Осознание → Рассмотрение → Покупка → Использование |
| **Действия (Actions)** | Что пользователь делает | Гуглит, сравнивает, кликает "Купить" |
| **Touchpoints** | Где "касается" бренда | Сайт, приложение, email, соцсети |
| **Эмоции** | Что чувствует | График вверх/вниз на каждом этапе |
| **Pain Points** | Где спотыкается | Долгая загрузка, сложная форма |
| **Opportunities** | Как улучшить | Упростить checkout, добавить чат |

---

# CJM — Пример "Заказ еды"

| Этап | Pain Point | Opportunity |
|------|------------|-------------|
| **Выбор** | Долго грузится | Загрузка < 2 сек |
| **Заказ** | Ввод адреса каждый раз | Сохранённые адреса |
| **Ожидание** | Не вижу курьера | Трекинг на карте |
| **Получение** | Еда остыла | Термосумка |

# Requirements Traceability

**Traceability** — отслеживание связей

**Связи:**
```
Business Req → User Req → FR → Test Cases
```

**Зачем:**
- Ничего не потеряется
- Понятно ЗАЧЕМ каждое требование
- Легко найти что не реализовано
- Оценить влияние изменений

---

# Traceability Matrix

| Business | User | FR | Test |
|----------|------|-----|------|
| BR-001: Продажи +25% | UR-001: Найти товар | FR-001: Фильтр цены | TC-001: Фильтр работает |
| BR-001: Продажи +25% | UR-002: Добавить в корзину | FR-002: Кнопка корзины | TC-002: Товар в корзине |
| BR-002: Меньше звонков | UR-003: Отследить заказ | FR-003: Статус заказа | TC-003: Статус обновляется |

**Читаем:** Бизнес хочет продажи → пользователь должен искать → нужен фильтр → проверяем тестом

# Путь требования

1. **Elicitation** — собрали (интервью, CJM)
2. **Документирование** — User Stories + AC
3. **Приоритизация** — MoSCoW, MVP
4. **Управление** — Traceability, CR
5. **Разработка** → **Тестирование** → **Релиз**
6. **Итерация** — добавляем Should, Could

> Твоя роль: провести требование от идеи до продакшена
