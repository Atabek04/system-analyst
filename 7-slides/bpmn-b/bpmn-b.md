# Pool — это бассейн

**Pool** — буквально «бассейн». Весь процесс — это один бассейн.

Один бассейн = одна организация = один процесс.

```
┌─────────────────────────────────────────┐
│  POOL: Центр выдачи ВУ                  │
│                                         │
│   ○ ──────────────────────────── ◉      │
│                                         │
└─────────────────────────────────────────┘
```

> Пока не думаем, кто что делает — просто очерчиваем границу нашего процесса.

<!--
Teacher Notes:
- Акцентируй: Pool — это граница "нашего мира". Всё, что снаружи — чужая организация, чужой Pool.
- ~1 мин
-->

---

# Lane — дорожка в бассейне

**Lane** — дорожка, разделённая верёвками. Каждый участник плывёт в своей.

Lane отвечает на вопрос **«КТО?»** и может обозначать:
- **роль** — Регистратор, Кассир, QA
- **отдел** — Бухгалтерия, Юридический
- **систему** — CRM, Платёжный сервис, Email-сервис

Все плывут в одном направлении — к одной цели. Никто не мешает соседу.

```
┌─────────────────────────────────────────┐
│  POOL: Центр выдачи ВУ                  │
├─────────────────────────────────────────┤
│  Lane: Заявитель                        │
├─────────────────────────────────────────┤
│  Lane: Регистратор                      │
├─────────────────────────────────────────┤
│  Lane: Инспектор                        │
└─────────────────────────────────────────┘
```

<!--
Teacher Notes:
- Спроси: "Сколько дорожек может быть в одном бассейне?" → Сколько угодно, но каждая — отдельная роль/система.
- ~2 мин
-->

# Lane — роль, не человек

**Роль ≠ человек.**

Иван работает и кассиром, и регистратором. Но:

- Задача «Принять пошлину» → дорожка **Касса**
- Задача «Проверить документы» → дорожка **Регистратор**

Завтра Иван уволится, на кассу выйдет Мария — задачи никуда не переедут. Диаграмма не сломается.

> **IT-пример:** задача «Написать тесты» — дорожка QA, даже если её иногда делает Backend-разработчик.

<!--
Teacher Notes:
- Разбери пример с Иваном вслух, потом спроси: "А если у нас нет отдельного QA, тесты пишет разработчик — как назовём дорожку?" → Всё равно QA или "Тестирование" — это роль, не человек.
- ~2 мин
-->

# Один Pool или два? Правило одно

**Вопрос:** ты контролируешь их внутренний процесс?

| Ситуация | Решение |
|---|---|
| Разные роли внутри одной организации | Lanes в одном Pool |
| Разные организации | Отдельные Pool |

**Пример: оформление загранпаспорта**

```
Один Pool «МВД»                   Отдельный Pool
├── Lane: Оператор ЦОН             «Налоговая служба»
├── Lane: Инспектор                (чёрный ящик — мы не знаем,
├── Lane: Архив                     как они проверяют долги внутри)
└── Lane: Касса
```

Оператор, инспектор, архив — все сотрудники МВД. Один бассейн, разные дорожки.
Налоговая — другое ведомство. Свои правила, своя система. Отдельный бассейн.

> Тест: «Если я позвоню директору и скажу "сделай иначе" — он меня послушает?» Да → Lane. Нет → отдельный Pool.

<!--
Teacher Notes:
- Спроси студентов: "Минздрав проверяет медсправку. Это Lane или Pool?" → Pool, мы не управляем их процессом
- Спроси: "А регистратор и инспектор в ЦОН — Lane или Pool?" → Lane, оба сотрудники одной организации
- Тест с директором — очень практичный, запоминается
- ~3 мин

# Pool = сервис, Lane = слой сервиса

В IT каждый **микросервис — отдельный Pool**. Lanes внутри — его внутренние слои.

```
┌─ POOL: Order Service ──────────────────────────┐
│ Lane: API Layer      │ 📥 POST /orders          │
├──────────────────────┼─────────────────────────┤
│ Lane: Business Logic │ ⚙ валидация → ⚙ расчёт  │
├──────────────────────┼─────────────────────────┤
│ Lane: Database       │ ⚙ INSERT orders         │
└──────────────────────┴─────────────────────────┘
         ┊ Message Flow (REST / Event)
         ▼
┌─ POOL: Payment Service ────────────────────────┐
│ Lane: API Layer      │ 📥 POST /charge          │
├──────────────────────┼─────────────────────────┤
│ Lane: Business Logic │ ⚙ проверка лимита        │
├──────────────────────┼─────────────────────────┤
│ Lane: Database       │ ⚙ UPDATE balance         │
└──────────────────────┴─────────────────────────┘
```

Order Service не знает, как Payment Service устроен внутри — только отправляет запрос и ждёт ответ.

<!--
Teacher Notes:
- Это прямая аналогия с МВД / Налоговой: два ведомства → два сервиса. Не контролируешь внутреннее устройство → отдельный Pool.
- Спроси: "Какой стрелкой соединяем два Pool?" → Message Flow, пунктир. (Забегаем вперёд — вернёмся к этому на следующем этапе.)
- ~2 мин

# Pool «Центр выдачи ВУ» с дорожками

```
┌──────────────────────────────────────────────────────┐
│ POOL: Центр выдачи водительских удостоверений        │
├──────────────────────────────────────────────────────┤
│ Lane: Заявитель      │ ○ → ▢ получить талон → ...   │
├──────────────────────┼──────────────────────────────┤
│ Lane: Регистратор    │ 👤 проверка документов        │
├──────────────────────┼──────────────────────────────┤
│ Lane: Инспектор      │ ⚙ база нарушений → 📤 запрос │  ← больше всего задач
│                      │ ✉ ожидание ответа             │    = вероятное узкое место
├──────────────────────┼──────────────────────────────┤
│ Lane: Касса          │ ✋ приём пошлины               │
├──────────────────────┼──────────────────────────────┤
│ Lane: Экзаменатор    │ ▢ теория → ▢ площадка        │
├──────────────────────┼──────────────────────────────┤
│ Lane: Сотрудник выд. │ 👤 печать → 👤 выдача ВУ      │
└──────────────────────────────────────────────────────┘
```

> Сама логика не изменилась — но теперь с первого взгляда видно, **кто перегружен**.

# Второй Pool + Message Flow

**Второй Pool** — внешняя организация, часто рисуется как "чёрный ящик" (без содержимого).

**Message Flow** — пунктирная стрелка с кружком на конце. Только она пересекает границы пулов.

**Правило:**
- Sequence Flow — сплошная, **только внутри одного пула**
- Message Flow — пунктирная, **только между пулами**
- Сплошная стрелка не пересекает границу пула. Никогда.

<!--
Teacher Notes:
- Это самое жёсткое правило BPMN. Запомнить раз и навсегда.
- Predict: тянут сплошную стрелку наружу — поправляй сразу
- ~3 мин
-->

---

# Пример: Центр выдачи ↔ Медлаборатория

```
┌─ POOL: Центр выдачи ВУ ──────────────┐
│  📤 Запрос в медлабораторию ─ ─ ─ ┐  │
│       │                           ┊  │
│       ▼                           ┊  │
│  ○✉ Ответ получен ◀ ─ ─ ─ ─ ─ ─ ─┊  │
└──────────────────────────────────┊───┘
                                   ┊  Message Flow
                                   ┊  (пунктир)
                                   ▼
┌─ POOL: Медицинская лаборатория (чёрный ящик) ─┐
│                                               │
└───────────────────────────────────────────────┘
```

> Чёрный ящик честно говорит: "что они там внутри делают — не наше дело".

**Аналог в IT:** `POOL: Интернет-магазин` ─ ─ ─▶ `POOL: Платёжный шлюз (чёрный ящик)`. Магазин отправляет запрос на списание — шлюз возвращает статус. Что происходит внутри шлюза — нас не касается.

<!--

- Объясни: это самый частый паттерн интеграции — мы зовём внешнюю систему и ждём ответ
- IT-аналог: любой API-вызов — мы → внешний сервис (чёрный ящик)
- ~3 мин
-->

**Карандаш, 6 минут. Выбери ОДИН сюжет с внешней организацией:**

- 💳 **Интернет-магазин ↔ Платёжный шлюз (Stripe / PayPal)** — redirect на оплату, webhook об успехе

# Sub-process (свёрнутый)

**Sub-process** — задача-папка, внутри которой свой собственный процесс

- Прямоугольник с символом `[+]` снизу
- На главной диаграмме — один блок
- Развернуть = открыть внутреннюю диаграмму

**Пример:**
```
... → [+] Сдача экзамена → ...
```

Внутри:
```
○ старт → ▢ Теория → ▢ Площадка → ▢ Город → ◉ конец
```

> Sub-process — это «зум-аут»: один прямоугольник снаружи, целая диаграмма внутри.

# Loop marker

**Loop marker** — значок повтора снизу задачи или подпроцесса

- Круглая стрелка `↻` под прямоугольником
- Заменяет рисование явной обратной стрелки
- Условие повтора пишется рядом

**Пример:**
```
[+] Сдача экзамена ↻
       (повторяется до 3 попыток
        или до успеха)
```

> Маркер цикла говорит: «эта штука может повториться» — без визуального беспорядка.

# Data Object

**Data Object** — любые данные, с которыми работают задачи. Не обязательно физический документ.

- Иконка листа с загнутым углом: `📄`
- Соединяется с задачей пунктирной ассоциацией
- Не управляет потоком — сопровождает его
- Живёт только внутри одного экземпляра процесса

| Физический документ | Цифровые данные |
|---|---|
| 📄 Медицинская справка | 📄 JSON с результатом скоринга |
| 📄 Паспорт | 📄 Токен авторизации |
| 📄 Заявление на бумаге | 📄 Список товаров в корзине |

> Data Object — это «данные, которые задача читает или создаёт». Бумага, файл, объект в памяти — неважно.

<!--
Teacher Notes:
- Частое заблуждение: "Data Object — это только бумага". Нет. Любые данные, которые задача получает на вход или отдаёт на выход.
- Подчеркни: Data Object — это НЕ задача и НЕ событие. Это артефакт. Поток через него не идёт.
- ~3 мин
-->

# Data Store

**Data Store** — постоянное хранилище
- Иконка цилиндра: `🗄`
- Переживает экземпляр процесса (в отличие от Data Object)
- Используется для баз данных, реестров, систем хранения

**Пример в Центре выдачи ВУ:**
- 🗄 CRM-система центра — куда регистратор записывает дело
- 🗄 База нарушений ПДД — откуда инспектор читает данные о лишении прав

> Data Object — одноразовая бумажка. Data Store — постоянная база.

> **В IT:** Data Object — JSON в теле запроса. Data Store — PostgreSQL, S3-бакет, Redis.

# Group

**Group** — визуальная рамка, объединяющая логически связанные шаги

- Прямоугольник с пунктирным контуром (штрих-пунктир)
- Не влияет на исполнение
- Может пересекать дорожки

**Пример:**
Внутри Sub-process «Сдача экзамена» — рамка-группа «Экзаменационные испытания» вокруг блоков теория/площадка/город.

> Group — чисто косметика. Sub-process — функциональная единица.

# Annotation

**Annotation** — комментарий для читателя

- Квадратная скобка с текстом: `[ ... ]`
- Соединяется ассоциацией
- Парсер процессов её игнорирует

**Пример:**
```
○⏱ 30 дней
   ┊
   ┊
[ "после 3 неудачных
   попыток подряд" ]
```

> Аннотация нужна там, где правило неочевидно из названия.

## Вариант А: Замена водительского удостоверения (ВУ)

**Условия:**
- Заявителю исполнилось 10 лет с даты выдачи ВУ — он пришёл менять
- Экзамены не нужны: нужны медицинская справка + пошлина + фото
- Если справка просрочена → на медкомиссию (внешняя организация)
- База нарушений проверяется автоматически параллельно с приёмом пошлины
- Если база вернула статус «лишён» → отказ + закрытие всех параллельных веток
- Замена ВУ хранится в CRM-системе центра

**Используй:** Pool + Lanes (мин. 4), второй Pool, Message Flow, AND, XOR, Signal или Terminate, Sub-process для «приём документов», Data Object «Личное дело», Data Store «CRM-система».

**Минимальный чек-лист правильного решения:**
