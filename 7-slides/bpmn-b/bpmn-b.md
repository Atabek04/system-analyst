# Типы задач (Task Types)

| Тип | Символ | Кто выполняет | Пример |
|-----|--------|---------------|--------|
| **User Task** | ▢ с человечком | Человек в системе | Менеджер заполняет форму одобрения |
| **Manual Task** | ▢ с рукой | Человек без системы | Курьер доставляет посылку |
| **Service Task** | ▢ с шестерёнкой | Система автоматически | Отправка email, обновление БД |
| **Send Task** | ▢ с конвертом (чёрный) | Отправка сообщения | Отправить заказ поставщику |
| **Receive Task** | ▢ с конвертом (белый) | Ожидание сообщения | Ждать подтверждение оплаты |

<!--
Teacher Notes:
- User Task vs Manual Task: ключевое отличие — есть ли система? User Task = человек работает В системе. Manual Task = человек работает БЕЗ системы.
- Service Task — всё, что система делает сама без участия человека
- В реальных проектах 80% задач — это User Task и Service Task
- ~4 мин
-->

# Task Markers — дополнительные обозначения

| Marker | Символ | Что значит | Пример |
|--------|--------|------------|--------|
| **Loop** | ↻ внизу задачи | Повторять пока условие не выполнится | Отправлять напоминание каждые 3 дня пока клиент не ответит |
| **Multiple Instance (parallel)** | ≡ три горизонтальные линии | Выполнить для КАЖДОГО элемента параллельно | Отправить уведомление КАЖДОМУ участнику встречи |
| **Multiple Instance (sequential)** | ≡ три вертикальные линии | Выполнить для каждого элемента по очереди | Проверить КАЖДЫЙ документ в заявке по очереди |

<!--
Teacher Notes:
- Loop — аналог while в коде: "делай X пока не Y"
- Multiple Instance — аналог forEach: "для каждого элемента из списка сделай X"
- Parallel MI: все одновременно, Sequential MI: строго по очереди
- Маркеры рисуются внизу по центру задачи, маленький символ
- ~3 мин
-->

# Pool — граница организации

**Pool** = контейнер, который представляет одного участника процесса (организация, компания, внешняя система)

- Каждый Pool — **отдельный** процесс
- Между пулами — **Message Flow** (пунктирная стрелка ⇢) — обмен информацией
- Sequence Flow (сплошная стрелка) **никогда** не пересекает границы пула

**Black Box Pool** — когда ты не знаешь (или не важно), что происходит внутри чужой организации. Просто прямоугольник с названием, без содержимого.

<!--
Teacher Notes:
- Pool = "чёрный ящик" другой организации. Ты отправляешь заказ поставщику — но не моделируешь что у него внутри
- Ключевое правило: sequence flow ВНУТРИ пула, message flow МЕЖДУ пулами
- Нарушение этого правила — самая частая ошибка у начинающих
- ~3 мин
-->

---

# Lane — роль внутри организации

**Lane** = горизонтальная полоса внутри Pool, показывает кто отвечает за какие задачи

- Lanes делят Pool на зоны ответственности: отделы, роли, должности
- Sequence Flow свободно пересекает Lanes — это всё один процесс внутри одной организации
- Каждая задача стоит в Lane того, кто её выполняет

**Когда использовать Lanes:**
- Когда важно показать **кто** делает каждый шаг
- Когда процесс проходит через несколько отделов
- Когда нужно выявить **handoff-ы** — передачи между отделами

<!--
Teacher Notes:
- Handoff — каждое пересечение стрелкой границы Lane. Чем больше handoff-ов, тем больше точек потери информации
- В AS-IS моделировании lanes сразу показывают, сколько раз задача "перепрыгивает" между отделами
- ~3 мин
-->

---

# Pool + Lane: визуальная схема

```
┌─────────────────────────────────────────────┐
│ Pool: Наша Компания                         │
│ ┌──────────────┐                            │
│ │ Lane: Закупки│  [Создать заявку] →        │
│ └──────────────┘            ↓               │
│ ┌──────────────┐            ↓               │
│ │ Lane: Финансы│  [Одобрить бюджет] →       │
│ └──────────────┘            ↓               │
│ ┌──────────────┐            ↓               │
│ │ Lane: Склад  │  [Принять товар]           │
│ └──────────────┘                            │
└─────────────────────────────────────────────┘
         ⇣ message flow         ⇡ message flow
┌─────────────────────────────────────────────┐
│ Pool: Поставщик (Black Box)                 │
└─────────────────────────────────────────────┘
```

- Message flow (пунктирные стрелки) — между нашей компанией и поставщиком

# Упражнение 3: Результат

**Pool "Наша Компания":**
- Lane Закупки: Start → Создать заявку на закупку (User Task) →
- Lane Финансы: → Проверить бюджет (User Task) → XOR: Одобрено?
  - Нет → Вернуть на доработку → (назад к заявке)
  - Да →
- Lane Закупки: → Отправить заказ поставщику (Send Task) ⇢
- ⇠ Получить подтверждение (Receive Task) →
- ⇠ Получить товар (Message Event) →
- Lane Склад: → Принять и проверить товар (Manual Task) → XOR: Всё ок?
  - Нет → Оформить возврат → End
  - Да → Обновить остатки (Service Task) → End

**Pool "Поставщик":** Black Box — message flow входит и выходит

# Subprocess — сложность под контролем

**Subprocess** — задача, внутри которой скрыт целый процесс

- Обозначается: прямоугольник со значком **+** внизу (collapsed)
- Можно развернуть — увидишь полную диаграмму внутри (expanded)

**Когда использовать:**
- Задача слишком сложная для одного прямоугольника (3+ шагов внутри)
- Один и тот же процесс используется в нескольких местах
- Диаграмма становится нечитаемой — пора группировать

**Пример:** "Проверка документов клиента" = subprocess, внутри: проверить паспорт → проверить справку о доходах → проверить кредитную историю

<!--
Teacher Notes:
- Subprocess = "глава в книге": у неё есть название, а детали — внутри
- Collapsed = видишь только название + значок "+". Expanded = видишь все шаги внутри
- Совет: если на диаграмме больше 15-20 элементов — ищи что свернуть в subprocess
- ~3 мин
-->

---

# Call Activity — переиспользование

**Call Activity** — ссылка на глобальный subprocess, который используется в разных процессах

- Обозначается: прямоугольник с **жирной рамкой**
- Отличие от Subprocess: Call Activity определён **один раз**, вызывается из **нескольких** процессов

**Пример:** Процедура KYC (Know Your Customer) — используется и при открытии счёта, и при выдаче кредита, и при оформлении страховки. Описываешь один раз, вызываешь из трёх разных процессов.

<!--
Teacher Notes:
- Call Activity — принцип DRY (Don't Repeat Yourself) в моделировании
- Если один и тот же набор шагов повторяется в 2+ процессах — выноси в Call Activity
- В инструментах (Camunda, Bizagi) Call Activity реально ссылается на другую диаграмму
- ~2 мин
-->

# Artifacts — дополнительная информация

| Artifact | Символ | Зачем |
|----------|--------|-------|
| **Text Annotation** | Квадратная скобка [ с текстом | Комментарий к элементу: пояснение, ограничение |
| **Data Object** | Лист с загнутым уголком 📄 | Документ: "Заявка", "Счёт", "Договор" |
| **Data Store** | Цилиндр 🗄 | База данных или хранилище |

- Artifacts **не влияют** на поток процесса — это дополнительная информация
- Связываются с элементами через **Association** (пунктирная линия без стрелки)

# AS-IS: Фиксируем текущий процесс

**AS-IS** = модель того, как процесс работает **прямо сейчас**, со всеми костылями

**Как собирать информацию для AS-IS:**
- **Gemba walk** — иди и наблюдай: смотри как люди реально работают, не как они описывают
- Интервью с участниками процесса: "Покажи мне шаг за шагом, что ты делаешь"
- Анализ существующих документов, инструкций, регламентов

**Что фиксировать:**
- Каждый шаг процесса (даже "глупые" ручные шаги)
- Кто выполняет (lanes)
- Сколько времени занимает каждый шаг
- Где процесс тормозит, где данные теряются

<!--
Teacher Notes:
- Gemba walk — термин из Lean Manufacturing. Буквально "иди и смотри"
- Важно: люди часто описывают процесс не так, как делают его на самом деле. Наблюдение > интервью
- Фиксируй ВСЁ, даже то что кажется мелочью — "Маша пересылает файл Коле по email" — это handoff, это потеря времени
- ~3 мин
-->

# Пример: AS-IS — Одобрение кредита в банке

**Реальный случай:** банк автоматизирует кредитные заявки

AS-IS процесс (бумажный):
1. Клиент заполняет бумажную анкету в отделении
2. Менеджер вручную вбивает данные в систему
3. Менеджер распечатывает анкету и несёт на подпись начальнику отдела
4. Начальник проверяет и подписывает (или возвращает)
5. Менеджер сканирует подписанную анкету
6. Менеджер отправляет скан в службу безопасности по email
7. СБ проверяет клиента (вручную, в нескольких системах)
8. СБ отправляет результат по email менеджеру
9. Менеджер вносит результат в систему
10. ...ещё 4 шага согласования

**14 шагов. 5 ручных пересылок. 3 ввода одних и тех же данных.**

<!--
Teacher Notes:
- Расскажи: без AS-IS разработчики просто перенесли этот процесс в систему один-в-один. Дорого и всё ещё криво.
- Спроси студентов: "Какие шаги здесь лишние? Какие можно объединить?"
- ~4 мин
-->

# TO-BE: Проектируем улучшенный процесс

**TO-BE** = как процесс **должен** работать после внедрения изменений

**Что меняем в AS-IS:**
- Убираем дублирующиеся шаги
- Автоматизируем ручные задачи
- Параллелизуем то, что шло последовательно
- Сокращаем handoff-ы между отделами

**TO-BE для кредитной заявки:**
1. Клиент заполняет онлайн-форму (User Task → Service Task: валидация)
2. Система автоматически проверяет кредитную историю (Service Task)
3. AND: Параллельно — проверка СБ + скоринг + проверка документов
4. Система формирует решение → Менеджер подтверждает (User Task)
5. Автоматическое уведомление клиенту (Service Task)

**14 шагов → 5. Ручных пересылок → 0. Время: дни → часы.**

<!--
Teacher Notes:
- Покажи side-by-side: AS-IS слева, TO-BE справа
- Подчеркни конкретные изменения: бумажная анкета → онлайн-форма, email пересылки → автоматическая маршрутизация, последовательные проверки → параллельные (AND gateway)
- Важно: TO-BE должен быть реалистичным, не фантазией. Учитывай ограничения: регуляции, бюджет, готовность людей
- ~4 мин
-->

---

# AS-IS → TO-BE: Что аннотировать

При сравнении двух моделей покажи:

| Что изменилось | AS-IS | TO-BE |
|---------------|-------|-------|
| Ручной ввод | Менеджер вбивает данные | Клиент вводит сам (онлайн-форма) |
| Последовательные проверки | СБ → скоринг → документы (по очереди) | Все три параллельно (AND) |
| Email-пересылки | 5 пересылок между отделами | 0 — автоматическая маршрутизация |
| Повторный ввод данных | 3 раза одни и те же данные | 1 раз — данные в системе |
| Бумажные подписи | Распечатка → подпись → скан | Электронное согласование |

# Оптимизация: ESIA Framework

**Четыре стратегии улучшения процесса (в порядке приоритета):**

| Стратегия | Что делаем | Пример |
|-----------|-----------|--------|
| **Eliminate** | Убрать шаг полностью | 3 из 5 подписей не нужны — убираем |
| **Simplify** | Упростить сложный шаг | Вместо заполнения 3 форм — одна |
| **Integrate** | Объединить handoff-ы | Два отдела делали по части — объединить в одного исполнителя |
| **Automate** | Заменить ручное автоматическим | Проверка политики расходов — автоматическая (Service Task) |

> Порядок важен: сначала убери лишнее, потом упрости, потом объедини, и только потом автоматизируй. Автоматизировать мусор — дорого и бессмысленно.

<!--
Teacher Notes:
- ESIA — фреймворк из Lean / BPM community. Порядок не случайный.

- Пример с 5 подписями: Eliminate (убрать 3 ненужные) → Simplify (одна форма вместо трёх) → Automate (автопроверка по лимитам) → итог: 1 подпись для сумм > порога, остальное автоматически.

# Как находить Bottleneck-и

**Bottleneck** (узкое место) — шаг, который замедляет весь процесс

**Индикаторы bottleneck-а на BPMN-диаграмме:**

- **Время ожидания >> время обработки** — задача выполняется 10 минут, но в очереди стоит 2 дня
- **Много handoff-ов** — каждый переход между Lanes = потенциальная задержка
- **Rework loops** — XOR gateway, ведущий назад ("вернуть на доработку") — значит качество на входе низкое
- **Последовательное вместо параллельного** — три проверки идут по очереди, хотя могли бы одновременно (AND)
- **Manual Task где мог бы быть Service Task** — человек делает то, что система сделает быстрее

<!--

- Rework loop — особенно коварный: каждый возврат удваивает время, а на диаграмме выглядит как маленькая стрелочка назад

# Метрики процесса

**Что измерять на AS-IS (чтобы сравнить с TO-BE):**

| Метрика | Что показывает | Как считать |
|---------|---------------|-------------|
| **Cycle Time** | Общее время от начала до конца | Start Event → End Event |
| **Processing Time** | Время полезной работы | Сумма времени всех Tasks |
| **Waiting Time** | Время ожидания | Cycle Time − Processing Time |
| **Handoff Count** | Количество передач между ролями | Сколько раз стрелка пересекает Lane |
| **Rework Rate** | Доля возвратов | % случаев, когда XOR loop срабатывает |

> Если Waiting Time > 70% от Cycle Time — процесс болен. Лечение: ESIA.

# Recap: Lesson B
