# Корень проблемы

**Главная проблема:**
- Не было **чёткого описания** того, ЧТО именно нужно делать
- Каждый представлял что-то своё в голове
- Никто не записал и не согласовал детали

**Решение:**
- **Требования** — это и есть такое описание
- Записанное, согласованное, понятное всем

> Требования — это мост между идеей заказчика и работой команды

# Определение

**Требование** — это описание того, что система должна делать (или каким свойством обладать).

**Ключевые свойства хорошего требования — SMART:**

| | Свойство | Значение |
|---|----------|----------|
| **S** — Specific | **Однозначное** | все понимают одинаково |
| **M** — Measurable | **Измеримое** | можно проверить цифрой или тестом |
| **A** — Achievable | **Реалистичное** | технически можно сделать |
| **R** — Relevant | **Необходимое** | есть причина зачем это нужно |
| **T** — Testable | **Проверяемое** | понятно как протестировать |

<!--

# Ответы: что не так?

| # | Требование | Что не так? |
|---|-----------|-------------|
| 1 | "Доступна 24/7/365 без исключений" | **Нереалистичное** — даже Google имеет даунтаймы; 100% uptime стоит бесконечных денег |
| 2 | "Интерфейс должен быть удобным" | **Неизмеримое** — что значит "удобный"? Нет цифры, нет критерия |
| 3 | "Логотип в 14 цветовых вариантах" | **Ненужное** — нет бизнес-причины; кому и зачем это нужно? |
| 4 | "Работать быстро" | **Непроверяемое** — как тестировщик проверит "быстро"? Нет условий теста |
| 5 | "Не должен изменять данные" | **Неоднозначное** — какие данные? Какой пользователь? Все поля или только некоторые? |

<!--
Teacher Notes:
Разбирай по одному. Ключевые моменты:
1. Нереалистичное — расскажи про "девятки" (99.9%, 99.99%) и что даже AWS гарантирует только 99.99%
2. Неизмеримое — спроси "удобный для кого? Для бабушки или для программиста?"
3. Ненужное — спроси "а заказчик заплатит за 14 вариантов логотипа? Зачем это бизнесу?"
4. Непроверяемое — "быстро" для пользователя = 1 сек, для заказчика = 5 сек, для разработчика = "не падает"
5. Неоднозначное — покажи как одно требование можно понять 3 способами

# Исправленные требования

| Было (плохо) | Стало (хорошо) |
|-------------|---------------|
| "Доступна 24/7/365 без исключений" | "Uptime ≥ 99.9%, плановое обслуживание ночью с уведомлением за 24ч" |
| "Интерфейс должен быть удобным" | "90% новых пользователей завершают регистрацию без обращения в поддержку" |
| "Логотип в 14 цветовых вариантах" | "Отчёт содержит логотип компании в корпоративных цветах (согласно брендбуку)" |
| "Работать быстро" | "Страница каталога загружается за < 2 сек при 500 одновременных пользователях" |
| "Не должен изменять данные" | "Пользователь с ролью 'Оператор' не может редактировать финансовые отчёты после утверждения" |

# Пирамида требований

**4 уровня требований (сверху вниз):**

```
           BUSINESS REQUIREMENTS
                    ↓
            USER REQUIREMENTS
                    ↓
       FUNCTIONAL REQUIREMENTS (FR)
                    ↓
    NON-FUNCTIONAL REQUIREMENTS (NFR)
```

**Связь:** каждый уровень вытекает из предыдущего

# Business Requirements

**Business Requirements** — зачем бизнесу этот проект?

**Характеристики:**
- Формулируются владельцами бизнеса
- Выражены в бизнес-терминах (деньги, время, доля рынка)
- Измеримы цифрами KPI
- Не про технологию, про деньги/клиентов/рынок

**Примеры:**
- "Увеличить онлайн-продажи на 25% за 6 месяцев"
- "Сократить время обработки заказа с 10 минут до 2 минут"
- "Привлечь 50 000 новых пользователей в первый квартал"

<!--
MEME: "Shut up and take my money" — но с подписью "Business Requirements в двух словах"
-->

---

# User Requirements

**User Requirements** — что пользователь хочет ДЕЛАТЬ?

**Характеристики:**
- Описывают действия/задачи пользователя
- Пишутся языком пользователя (не технический жаргон)
- Фокус на ЗАЧЕМ пользователь это делает (ценность)
- Часто в формате User Story

**Примеры:**
- "Зарегистрироваться в системе через email"
- "Найти товар по категории и цене"
- "Отследить статус доставки заказа"
- "Оставить отзыв о товаре"

<!--
Teacher Notes:
Спроси: "В чём разница между Business Req 'увеличить продажи на 25%' и User Req 'найти товар по категории'?" Ответ: первое — цель бизнеса, второе — что пользователь должен уметь делать чтобы эта цель достигалась.
-->

---

# Functional Requirements (FR)

**Functional Requirements** — конкретное ПОВЕДЕНИЕ системы

**Характеристики:**
- Описывают ЧТО система делает (действие, функция)
- Формат: "Когда пользователь делает X, система делает Y"
- Проверяемы тестами
- Детализируют User Requirements

**Примеры:**
- "При нажатии 'Купить' система создаёт заказ и отправляет email"
- "Система блокирует аккаунт после 5 неудачных попыток входа"
- "При вводе промокода система пересчитывает сумму со скидкой"

<!--
VISUAL: Блок-схема простого процесса: кнопка → система → результат
-->

---

# Non-Functional Requirements (NFR)

**Non-Functional Requirements** — КАК система работает (качество)

**Категории NFR:**
- **Performance** — скорость, время отклика
- **Security** — защита данных, аутентификация
- **Usability** — удобство использования
- **Reliability** — стабильность, uptime
- **Scalability** — способность расти под нагрузкой

**Примеры:**
- "API отвечает за < 200 мс в 95% запросов"
- "Пароли хранятся в зашифрованном виде (bcrypt)"
- "Сайт доступен 99.9% времени"

<!--
MEME: "It works on my machine" — с подписью "Когда забыли про NFR"
-->

---

# FR vs NFR — В чём разница?

| Критерий | FR | NFR |
|----------|-----|-----|
| **Вопрос** | ЧТО делает? | КАК делает? |
| **Фокус** | Функции, действия | Качество, свойства |
| **Пример** | Можно сбросить пароль | Сброс за < 5 секунд |
| **Тестирование** | Функциональные тесты | Нагрузочные, security |
| **Если нарушено** | Не работает | Работает, но плохо |

<!--
Teacher Notes:
Аналогия: FR — это "машина должна ехать вперёд/назад/тормозить" (функции), NFR — это "машина разгоняется до 100 км/ч за 8 секунд, расход 6л/100км" (характеристики). Обе нужны!
-->

# Пирамида в действии — Пример

**Кейс: Интернет-магазин одежды**

1. **Business Req**: Увеличить конверсию с 2% до 5% за квартал
   — *конверсия = % посетителей, совершивших покупку*
2. **User Req**: Видеть товар на модели моего размера
3. **FR**: При выборе размера фото обновляется на соответствующий
4. **NFR**: Фото загружается за < 1 сек, работает на мобильных

**Видишь связь?** Всё идёт от бизнес-цели вниз к деталям реализации

# Recap: Что это и Какие бывают

| Концепция | Суть | Пример |
|-----------|------|--------|
| **Требование** | Описание что/как система должна работать | "Страница грузится < 2 сек" |
| **Свойства** | Измеримое, проверяемое, однозначное | Цифры, тесты |
| **Business Req** | Зачем бизнесу проект | "Увеличить продажи на 20%" |
| **User Req** | Что пользователь хочет делать | "Найти товар по фильтру" |
| **FR** | Конкретное поведение системы | "Кнопка создаёт заказ" |
| **NFR** | Качество работы системы | "API отвечает < 200 мс" |

> Требования — это фундамент проекта. Плохие требования → плохой продукт.
