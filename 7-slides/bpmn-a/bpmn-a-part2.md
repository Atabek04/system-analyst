# Чего не хватает в нашем арсенале

Три ситуации, которые Task и Gateway **не умеют** показать:

- Процесс **ждёт** время — 30 минут таймера доставки, 5 дней на ответ ведомства
- Извне **прилетает** сообщение — внешняя система подтвердила справку
- Внутри задачи **сломалось** — терминал завис во время оформления

> **Task** = *мы* делаем.
> **Gateway** = *мы* выбираем по данным.
> А здесь — *с нами случается*.

Для этого BPMN даёт третий класс элементов — **Event (событие)**.

<!--
Teacher Notes:
- Ключевая мысль: Task и Gateway описывают наши активные действия. Event — реакция на внешний мир или время.
- ~2 мин

# Task vs Gateway vs Event

|               | Кто активен              | Пример в ЦОН                                  |
| ------------- | ------------------------ | --------------------------------------------- |
| **Task ▢**    | Мы работаем              | Регистратор проверяет паспорт                 |
| **Gateway ◇** | Мы решаем по данным      | Возраст ≥ 18?                                 |
| **Event ○**   | С нами что-то происходит | Пришёл ответ МВД / истекли 7 дней / АИС упала |

**Запомни одну строчку:**

> **Gateway смотрит в данные. Event реагирует на мир.**

# Timer Event

**Timer Event** — поток ждёт назначенное время

- Круг с иконкой часов: `○⏱`
- Не "задача", а событие — никто ничего не делает, время просто идёт
- Может задавать: интервал (30 минут), конкретную дату, цикл

**Пример: доставка пиццы**
```
○ Заказ принят
    ↓
⚙ Передать заказ на кухню
    ↓
○⏱ 30 минут
    ↓
⚙ Обновить статус «Задержка»
    ↓
▢ Ожидание доставки
```

**Пример: пересдача экзамена**
```
◇× «Сдал?»
  нет ↓
 ○⏱ 7 дней
    ↓
▢ Пересдать теорию
```

<!--
Teacher Notes:
- Timer Event делает явным то, что иначе "живёт в голове" сотрудников
- Виды Timer: 30 минут (PT30M), 7 дней (P7D), конкретная дата (ISO-8601)
- Пример с пиццей — показывает что никто не "выполняет" ожидание. Пример с пересдачей — покажи сразу второй паттерн.
- Элементы для bpmn.io: Start Event → Service Task "Передать заказ" → Intermediate Timer Catch Event "30 минут" → Service Task "Обновить статус"
- ~3 мин
-->

# Message Event (intermediate)

**Message Event** — момент, когда из-за границы процесса прилетает сообщение

- Круг с иконкой конверта: `○✉`
- Не задача — никто ничего не делает, процесс просто ждёт
- Часто стоит после Send Task

**Пример:**
```
▢ Принять медсправку
        ↓
📤 Отправить запрос в Минздрав
        ↓
   ○✉ Ответ получен
        ↓
  ◇× «Справка действительна?»
```

> Message Event = «что-то случилось с процессом». Receive Task = «мы активно ждём».

<!--
Teacher Notes:
- Не торопись объяснять разницу сам — она раскроется на следующем слайде через вопрос
- Элементы для bpmn.io: User Task "Принять медсправку" → Send Task "Отправить запрос в Минздрав" → Intermediate Message Catch Event "Ответ получен" → Exclusive Gateway "Справка действительна?"
- ~2 мин
-->

# Receive Task vs Message Catch Event

Оба ждут сообщения. Но структурно — разные элементы.

|                          | `○✉` Message Catch Event | `▢✉` Receive Task |
| ------------------------ | ------------------------ | ----------------- |
| Смысл                    | *что-то произошло*       | *мы активно ждём* |
| Boundary Timer / Error   | ❌                        | ✅                 |
| Loop (несколько ответов) | ❌                        | ✅                 |
| Event-Based Gateway      | ✅ обязательно            | ❌                 |

**Правило:**
- По умолчанию → `○✉` Message Catch Event
- Нужен таймаут или ошибка на ожидание → `▢✉` Receive Task

<!--

- Главный вывод: таймаут на ожидание = Receive Task + Boundary Timer
- ~3 мин

# Boundary Error Event

**Boundary Error Event** — аварийный выход из задачи

- Круг с молнией ⚡, прицеплен к границе задачи
- Если внутри задачи случилась ошибка — поток уходит по альтернативной ветке
- Сама задача прерывается

**Пример: выдача талона электронной очереди**
```
○ Заявитель вошёл в зал
         ↓
👤 Выбрать услугу на терминале
         ↓
   ┌────────────────────┐
   │ ⚙ queue-service    │⚡ ─→ ✋ Оператор выдаёт
   │   печатает талон   │       бумажный талон
   │   "A-047"          │       и пишет номер
   └────────────────────┘       в журнал
         ↓ (норма)                   ↓
   ▢ Ожидание вызова       ▢ Ожидание вызова
         на табло               по списку оператора
```

*queue-service упал — очередь не останавливается, операторы переходят на ручной режим.*

> Boundary Event — это "запасной выход" из горящего здания.

<!--
Teacher Notes:
- Это первый "не последовательный" элемент — событие сидит на границе, а не в потоке
- Реальный сценарий: queue-service — микросервис, падает вместе с сетью или БД; операторы обучены переходить на ручной режим
- Виды граничных событий: Error, Timer (таймаут на саму задачу), Message, Cancel
- Элементы для bpmn.io: Start Event "Заявитель вошёл в зал" → User Task "Выбрать услугу на терминале" → Service Task "queue-service печатает талон" (с Boundary Error Event на границе) → норма: Task "Ожидание вызова на табло" / по ошибке: Manual Task "Оператор выдаёт бумажный талон и пишет номер в журнал" → Task "Ожидание вызова по списку оператора"
- ~3 мин
-->

**Проверка МВД вернула: заявитель в розыске.**

Это не просто «отказ по текущему окну». Эту новость должны узнать сразу все:

- **Охрана ЦОН** — задержать до приезда наряда
- **Соседние окошки** — у него могут быть ещё заявления (паспорт, прописка) — заблокировать
- **Начальник смены** — вызвать наряд, составить акт
- **Архив** — пометить дело красным флагом

Мы не знаем заранее, кто именно отреагирует — просто объявляем факт.

Это «адресное письмо» одному получателю — или «объявление по громкой связи»?

# Signal Event

**Signal** — широковещательный сигнал, без конкретного адресата
- Круг с треугольником: `○▲`
- Ловят все, кто подписан на этот сигнал

---

# Signal в e-commerce: `OrderPaid`

В интернет-магазине клиент оплатил заказ. Платёжный шлюз вернул `success`.

```
⚙ Списать деньги с карты
        ↓
⚙ Ответ шлюза: success
        ↓
   ○▲ Signal "OrderPaid"
```

**Кто ловит этот сигнал — один из десятков подписчиков:**

- 📦 **Warehouse** — резервирует товар, печатает стикер
- 🚚 **Shipping** — создаёт накладную, вызывает курьера
- ⭐ **Loyalty** — начисляет бонусные баллы
- 📧 **Email-сервис** — отправляет чек и трек-номер
- 📊 **Analytics** — пишет метрику выручки
- 🔍 **Fraud** — сканирует на подозрительные паттерны

> Платёжный сервис **не знает** про склад, доставку и лояльность. Он просто кричит `OrderPaid` — а подписчики сами решают, что с этим делать.

<!--
Teacher Notes:
- Это каноничный пример event-driven архитектуры в e-commerce (Shopify, Amazon, Stripe webhooks)
- Ключевой момент: завтра маркетинг подключит ещё один сервис ("рекомендации"), он просто подпишется на OrderPaid — платёжный сервис трогать не нужно. Это суть Signal.
- Сравни с Message: если бы платёжный сервис слал 6 отдельных сообщений — пришлось бы хардкодить всех адресатов
- Элементы для bpmn.io: Service Task "Списать деньги с карты" → Service Task "Ответ шлюза: success" → Intermediate Signal Throw Event "OrderPaid"
- ~3 мин
-->

# Signal в ЦОН: `Розыск`

```
⚙ Запрос в реестр МВД
        ↓
⚙ Ответ: статус заявителя
        ↓
  ◇× «В розыске?»
   да ↓
   ○▲ Signal "Розыск"
   (ловят: охрана, соседние окошки,
    начальник смены, архив)
```

> ⚠️ **Важно:** просто вернуть заявителю «отказ» и отпустить — это **глупо и опасно**. Человек в розыске не должен уйти из ЦОН свободно. Signal запускает реальные действия: охрана задерживает, соседние окошки блокируют его другие заявления, начальник вызывает наряд.

> Signal — "крикнуть всем". Message — "адресное письмо одному получателю".

<!--
Teacher Notes:
- Главная мысль: Signal — это не "красивый способ показать отказ". Это механизм запуска реакций у тех, кто подписан.
- Подчеркни: если аналитик рисует "в розыске → End Event" и на этом всё — он не понял задачу. Процесс должен иметь последствия за пределами текущей ветки.
- Ключевое отличие Signal vs Message:
  - Message — точка-точка, один конкретный получатель (мы знаем кому)
  - Signal — широковещание, ловят все кто подписан (мы не знаем кто именно)
- Почему не Message: адресатов несколько, состав может меняться (завтра подключится ещё одна система), и отправитель не должен про них знать
- Элементы для bpmn.io: Service Task "Запрос в реестр МВД" → Service Task "Ответ: статус заявителя" → Exclusive Gateway "В розыске?" → Intermediate Signal Throw Event "Розыск"
- ~3 мин
-->

# Terminate End Event

**Terminate End** — мгновенно убивает ВЕСЬ процесс

- Жирный круг с закрашенным кружком внутри: `◉●`
- Гасит все активные параллельные ветки
- Используется при «фатальных» отказах, когда продолжать бессмысленно

**Пример: найм кандидата**
```
○ Старт: кандидат подал заявку
        ↓
✋ Провести скрининг резюме
        ↓
        ◇+ AND-split
       /          |             \
✋ Техническое  👤 HR-интервью   ⚙ Проверка СБ
  интервью       (мотивация,      (судимости,
  (алгоритмы,    зарплата,        соц.сети,
   code review)  культура)        рекомендации)
       ↓              ↓                ↓
  ◇× «Прошёл?»   ◇× «Подходит?»  ◇× «Чисто?»
   нет ↓  да→     нет ↓  да→      нет ↓  да→
   ◉● Terminate   ◉● Terminate    ◉● Terminate
                        ↓ (все три «да»)
                    ◇+ AND-join
                        ↓
              ✋ Финальное решение с оффером
                        ↓
               ○ Конец: оффер отправлен
```

Провал **любой** ветки → `◉●` Terminate → остальные две останавливаются немедленно.

> Обычный End закрывает только свою ветку. Terminate — весь процесс, включая все параллельные.

# Terminate End Event: важная тонкость

**Terminate убивает только то, в чём находится.**

Если `◉●` стоит в **основном процессе** — гасится весь process instance. Именно это мы видели в примере с наймом.

Но если `◉●` стоит **внутри Sub-process** — он закроет только этот sub-process. Задачи снаружи продолжат выполняться. Например, «Отправить письмо об отказе» после sub-process никуда не денется — оно всё равно запустится.

В линейном процессе без параллельных веток Terminate и обычный End ведут себя **одинаково**. Разница видна только когда есть что гасить.

> Terminate внутри Sub-process = занавес в одной комнате, не во всём доме.

# Сюжет A: Онлайн-запись к врачу

Пациент выбирает врача и время на портале. Портал отправляет запрос в МИС (медицинская информационная система) и ждёт подтверждения.

**Подсказки:**
- Портал отправил запрос → **ждём ответа МИС** — что поставить? (`○✉` или `▢✉`?)
- МИС не ответила за **2 часа** — напомни пациенту попробовать снова
- Портал **упал** прямо во время записи — регистратор записывает вручную по телефону
- Запись подтверждена → **уведомить** и пациента, и врача, и администратора кабинета

**Используй:** Message, Receive Task, Timer, Boundary Error, Signal

---

# Сюжет B: Выдача кредитной карты в банке

Клиент подал заявку. Банк параллельно запускает три проверки: кредитная история (БКИ), санкционные списки (внешний реестр), верификация личности (фото + паспорт).

**Подсказки:**
- Три проверки идут **одновременно** — как запустить?
- БКИ не ответил за **5 минут** — продолжаем без него (таймаут на ожидание → нужен `▢✉` + Boundary Timer)
- Клиент попал в санкционный список → **немедленно стоп**, остальные проверки гасить
- Все три прошли → финальное решение андеррайтера

**Используй:** AND-split/join, Receive Task, Boundary Timer, Terminate End

---

# Сюжет C: Доставка заказа курьером

Заказ собран на складе. Система назначает курьера и ждёт подтверждения. Курьер забирает заказ и везёт клиенту.

**Подсказки:**
- Курьер **не подтвердил** маршрут за 30 минут → переназначить другого
- Платёжный терминал курьера **упал** при оплате на месте → клиент платит наличными (Boundary Error)
- Клиент **отменил заказ** пока курьер в пути → Signal `OrderCancelled` (склад, биллинг, курьер — все должны узнать)

**Используй:** Timer, Boundary Error, Signal Throw, Message

# Задание: упрощённый процесс выдачи ВУ

**Нарисуй на листе диаграмму со следующими правилами:**

1. Старт — заявитель пришёл в Мобильный ЦОН
2. Регистратор проверяет документы (User Task)
3. **XOR**: документы полные? нет → отказ; да → дальше
4. **AND**: параллельно — проверка в базе данных (Service) и приём пошлины (Manual)
5. После — экзамен (один Task пока)
6. **XOR**: сдал? нет → ⏱ ждём 7 дней → петля; да → дальше
7. Финал — ВУ выдано

**Используй:** Start/End, Task (User/Service/Manual), Sequence Flow, XOR, AND, Timer Event.
