# Elicitation — Что это?

**Elicitation** (сбор требований) — процесс извлечения требований из разных источников

**Почему "извлечения"?**
- Требования редко приходят готовыми
- Заказчик часто не знает что именно хочет
- Пользователи описывают проблемы, но не решения
- Твоя задача — "выудить" реальные потребности

**Источники требований:**
- Stakeholders (заказчик, пользователи, команда)
- Документы (процессы, регламенты, аналитика)
- Конкуренты и рынок
- Наблюдение за реальным использованием

<!--

# Техника 1 — Интервью

**Интервью** — личная беседа один на один с заинтересованной стороной

**Когда использовать:**
- Нужно глубокое понимание проблемы
- Есть ключевой эксперт (владелец бизнеса)
- Тема чувствительная

**Типы вопросов:**
- **Открытые**: "Расскажи о проблемах текущего процесса"
- **Закрытые**: "Используете ли вы мобильное приложение?"
- **Уточняющие**: "Что вы имеете в виду под 'удобным'?"

**Плюсы:** глубина, доверие, гибкость
**Минусы:** долго, дорого, мнение одного человека

# Техника 2 — Воркшоп

**Воркшоп** (Workshop) — групповая сессия с несколькими участниками

**Когда использовать:**
- Нужно согласовать требования между разными отделами
- Мозговой штурм новых идей
- Конфликтующие мнения — нужен консенсус

**Форматы:**
- **JAD** — структурированная сессия с фасилитатором
- **Brainstorming** — генерация идей без критики
- **Focus Group** — обсуждение конкретной темы

**Плюсы:** быстро, вовлечение, консенсус
**Минусы:** сложно модерировать, доминирующие личности

# Техника 3 — Наблюдение

**Наблюдение** — смотришь как пользователь работает сейчас (job shadowing)

**Когда использовать:**
- Пользователи не могут объяснить словами что делают
- Хочешь найти неочевидные проблемы
- Процесс сложный и запутанный

**Как проводить:**
- Сидишь рядом с пользователем
- Молча наблюдаешь и записываешь
- Задаёшь уточняющие вопросы после

**Плюсы:** видишь реальность, находишь скрытые проблемы
**Минусы:** долго, эффект наблюдателя

# Техника 4 — Опросы

**Опросы** (Surveys) — массовый сбор мнений через анкеты

**Когда использовать:**
- Нужно мнение МНОГИХ пользователей (сотни/тысячи)
- Есть конкретные вопросы с вариантами ответа
- Ограничен бюджет/время

**Типы вопросов:**
- **Шкала Ликерта**: "Оцените от 1 до 5"
- **Множественный выбор**: A/B/C/D
- **Открытый ответ**: "Опишите проблему"

**Плюсы:** быстро, дёшево, большая выборка
**Минусы:** низкий отклик, нет глубины

<!--

-->

# Техника 5 — Анализ документов

**Анализ документов** — изучение существующих материалов

**Что анализировать:**
- Текущие регламенты и инструкции
- Аналитику (Google Analytics, логи)
- Жалобы и отзывы пользователей
- Документацию конкурентов

**Когда использовать:**
- Перед интервью (чтобы задавать умные вопросы)
- Для понимания контекста
- Есть legacy-система

**Плюсы:** объективные данные, не отнимает время людей
**Минусы:** документы могут быть устаревшими

# User Story — Формат

**User Story** — описание функции с точки зрения пользователя

**Классический формат:**

**"Как [роль], я хочу [действие], чтобы [ценность]"**

**Пример:**
"Как покупатель, я хочу добавлять товары в избранное, чтобы быстро найти их потом"

**3 части обязательны:**
1. **Роль** — кто этот пользователь
2. **Действие** — что он хочет сделать
3. **Ценность** — зачем, какая польза

<!--
VISUAL: Карточка User Story с подсветкой трёх частей разными цветами
-->

---

# Почему важна часть "чтобы"

**Сравни:**

**Плохо:** "Как пользователь, я хочу сбросить пароль"
**Хорошо:** "Как пользователь, я хочу сбросить пароль, чтобы восстановить доступ если забыл"

**В чём разница?**
- Часть "чтобы" объясняет ЗАЧЕМ
- Без неё непонятна мотивация
- Команда может сделать не то решение

**Пример:**
- Если цель "восстановить доступ" → сброс по email/SMS
- Если цель "сменить на более безопасный" → проверка старого пароля

<!--
Teacher Notes:
Спроси: "Какая ещё может быть причина сбросить пароль?" (утечка данных, требование политики безопасности).
-->

# INVEST — Критерии хорошей User Story

Хорошая User Story должна быть **INVEST:**

- **I — Independent** (Независимая): можно делать в любом порядке
- **N — Negotiable** (Обсуждаемая): детали уточняются
- **V — Valuable** (Ценная): даёт пользу
- **E — Estimable** (Оцениваемая): команда может оценить
- **S — Small** (Маленькая): можно сделать за 1 спринт
- **T — Testable** (Тестируемая): понятно как проверить

<!--
VISUAL: Акроним INVEST вертикально с иконкой для каждой буквы
-->

---

# INVEST — Примеры

**Плохая User Story:**
"Как админ, я хочу управлять всеми пользователями в системе"

**Проблемы:**
- **Not Small** — слишком большая (месяцы работы)
- **Not Estimable** — слишком расплывчатая
- **Not Testable** — что значит "управлять всеми"?

**Хорошая (разбитая):**
- "Как админ, я хочу создавать пользователей, чтобы дать доступ новым сотрудникам"
- "Как админ, я хочу блокировать пользователей, чтобы отозвать доступ уволенных"
- "Как админ, я хочу назначать роли, чтобы контролировать уровень доступа"

<!--
Teacher Notes:
Большую User Story нужно ДРОБИТЬ на маленькие. Каждая маленькая — ценная сама по себе.
-->

---

# Хорошие vs Плохие User Stories

| Плохая | Хорошая |
|--------|---------|
| "Красивый дизайн" | "Видеть крупные фото, чтобы оценить детали" |
| "Интеграция с 1C" | "Как бухгалтер, чтобы заказы попадали в 1C автоматически" |
| "Добавить поиск" | "Как гость, искать товары по названию" |
| "Всё работало быстро" | "Поиск выдаёт результаты < 1 сек" |

# Job Story — Альтернатива

**Job Story** — фокус на ситуацию/контекст, а не роль

**Формат:**
**"Когда [ситуация], я хочу [действие], чтобы [результат]"**

**Пример:**
"Когда я захожу на сайт с телефона в метро, я хочу видеть упрощённую версию, чтобы быстро найти товар при плохом интернете"

**Когда Job Story лучше:**
- Контекст важнее роли
- Один пользователь в разных ситуациях
- Хочешь подчеркнуть КОГДА возникает потребность

<!--
Teacher Notes:
User Story — "Кто ты?", Job Story — "В какой ситуации ты?". Один человек в офисе с WiFi и в метро — разные ситуации.
-->

# Acceptance Criteria — Что это?

**Acceptance Criteria (AC)** — условия, при которых User Story считается выполненной

**Зачем нужны:**
- Разработчик понимает ЧТО делать
- Тестировщик знает ЧТО проверять
- Нет споров "готово или нет"

**Характеристики хороших AC:**
- Конкретные и проверяемые
- Написаны ДО начала разработки
- Покрывают happy path + edge cases

> Acceptance Criteria — это Definition of Done для User Story

<!--
VISUAL: Чек-лист с галочками — символ AC
-->

# Given-When-Then формат

**Стандартный формат Acceptance Criteria:**

```
Given [начальное состояние]
When [действие пользователя]
Then [ожидаемый результат]
```

**Пример для "Добавить в избранное":**

```
Given я авторизованный пользователь
  And я на странице товара
When я нажимаю "Добавить в избранное"
Then товар сохраняется в списке избранного
  And появляется уведомление "Добавлено"
  And иконка меняется на заполненное сердечко
```

<!--
Teacher Notes:
Given — "дано" (предусловия), When — "когда" (триггер), Then — "тогда" (результат).
-->

---

# Пример 1 — Сброс пароля

**User Story:**
"Как пользователь, я хочу сбросить пароль, чтобы восстановить доступ"

**AC1: Запрос на сброс**
```
Given я на странице входа
When нажимаю "Забыли пароль?", ввожу email, нажимаю "Отправить"
Then система отправляет письмо со ссылкой
  And показывает "Проверьте почту"
```

**AC2: Установка нового**
```
Given я получил письмо со ссылкой
When перехожу по ссылке, ввожу новый пароль (мин. 8 символов)
Then система сохраняет новый пароль
  And старый больше не работает
```

---

# Пример 2 — Фильтр по цене

**User Story:**
"Как покупатель, я хочу фильтровать по цене, чтобы найти подходящие бюджету"

**AC1: Применение фильтра**
```
Given я на странице каталога
When устанавливаю диапазон 1000-5000₽, нажимаю "Применить"
Then показываются только товары в этом диапазоне
```

**AC2: Сброс фильтра**
```
Given я применил фильтр
When нажимаю "Сбросить"
Then показываются все товары
```

**AC3: Нет товаров (edge case)**
```
Given диапазон 1000000-2000000₽
When нажимаю "Применить"
Then показывается "Товары не найдены"
```

<!--
Teacher Notes:
AC3 — edge case. Хорошие AC покрывают и happy path и крайние случаи.
-->

---

# Пример 3 — Корзина

**User Story:**
"Как покупатель, я хочу добавлять товары в корзину"

**AC1: Добавление**
```
Given я на странице товара "Ноутбук HP"
When нажимаю "В корзину"
Then товар появляется в корзине
  And счётчик увеличивается на 1
```

**AC2: Изменение количества**
```
Given в корзине 1 товар
When увеличиваю количество до 3
Then сумма пересчитывается (цена × 3)
```

**AC3: Удаление**
```
Given в корзине 2 товара
When нажимаю "Удалить" у одного
Then товар исчезает, сумма пересчитывается
```

| **Job Story** | "Когда [ситуация], хочу..." |
