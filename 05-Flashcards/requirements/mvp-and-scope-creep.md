Что такое MVP и что значит "viable"?
Back: **MVP** (Minimum Viable Product) — версия с минимальным набором функций, которая УЖЕ решает проблему пользователя. "Viable" означает, что продукт работает и приносит ценность — это настоящий продукт, а не макет. Цель: выпустить быстро, получить обратную связь, итерировать.

Coding Questions
Почему "скейтборд → самокат → велосипед → машина" — правильная аналогия MVP?
Back: Потому что на КАЖДОМ этапе пользователь может "ехать" (продукт работает). Неправильный подход — "колесо → шасси → кузов → машина", где ничего не работает до самого конца. MVP — это не "половина продукта", а простой, но полноценный продукт. Каждая итерация приносит пользу и генерирует обратную связь.

Как связаны MVP и MoSCoW?
Back: **MVP = Must have требования из MoSCoW**. Процесс:
1. Собрать все User Stories
2. Приоритизировать по MoSCoW
3. Взять только Must have → это твой MVP
4. v2.0 добавляет Should have, v3.0 добавляет Could have
Пример: MVP = Каталог + Корзина + Заказ + Оплата. v2.0 = + Избранное + Фильтры + Отзывы.

Что такое Scope Creep и почему это опасно?
Back: **Scope Creep** — неконтролируемый рост требований в ходе проекта. Признаки: постоянные "маленькие" добавления, "это же быстро!", дедлайны не сдвигаются, а работы прибавляется.
Опасно потому что: сроки срываются, бюджет превышается, качество падает, команда выгорает.

Coding Questions
Как предотвратить Scope Creep?
Back:
1. **Базовые требования (Baseline)** — формально зафиксировать объём на старте проекта
2. **Процесс Change Request** — любое новое требование проходит: запрос → оценка влияния → одобрение/отклонение → обновление базовой линии
3. **Подход "да, но"** — "Мы можем добавить фильтры, но это +2 недели к дедлайну"
4. **Компромиссы (Trade-offs)** — "Фильтры ИЛИ профиль пользователя — что выбираем?"
5. **Регулярные обзоры скоупа** — напоминать всем, о чём договорились

Что такое Change Request (CR) и как выглядит процесс?
Back: **Change Request** — формальный процесс управления изменениями объёма:
1. **Запрос**: ЧТО хотят и ЗАЧЕМ
2. **Оценка**: время, стоимость, риски
3. **Решение**: одобрить, отклонить или отложить
4. **Документирование**: обновить базовую линию
Пример: CR-001: "Добавить фильтр по размеру. Причина: 60% пользователей ищут по размеру (аналитика). Оценка: 3 дня разработки + 1 день тестирования. Решение: Одобрено, +4 дня к дедлайну."
