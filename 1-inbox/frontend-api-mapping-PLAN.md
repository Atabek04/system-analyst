## Главная идея урока (одно предложение)

**UI это просто JSON, нарисованный на экране.** Frontend делает запрос → получает JSON → раскладывает поля по местам на странице. Всё, что вы видите в приложении, это чьи-то поля из ответа сервера.

Если студент это понял, он навсегда перестаёт бояться API: страница = данные + шаблон.

## Хук и проблема (productive failure)

**Хук:** Откройте YouTube. Заголовок видео, число просмотров, аватар канала, лента снизу. Откуда браузер всё это взял? Он не хранит это у себя.

**Проблема:** Frontend (витрина) пустой по умолчанию, это просто шаблон с пустыми местами. Данные живут на сервере. Кто-то должен их запросить и разложить по местам. Как именно пустой шаблон превращается в заполненную страницу?

Дать студенту подумать: «если бы вы делали страницу профиля, откуда взяли бы имя и аватар?»

---

## Ключевой визуальный приём урока (важно!)

Каждый сценарий показываем **split-screen**: слева JSON-ответ, справа макет UI, между ними **стрелки маппинга** поле → элемент.

Это ядро урока. Не описываем словами «поле title идёт в заголовок», а **показываем стрелкой** на диаграмме и ссылаемся на неё (по нашим новым правилам text+diagram: диаграмма несёт маппинг, текст объясняет смысл).

Цветовая связка: одно и то же поле подсвечено одним цветом в JSON и в UI (color-coding снижает нагрузку на поиск соответствий, доказано в research по redundancy).

## Сценарии (от простого к сложному)

### Сценарий 1 — Список элементов (GET коллекция) ⭐ ядро
**Сайт:** Instagram лента / YouTube главная
**Endpoint:** `GET /posts` (или `/feed`)
**Request:** без тела, метод GET
**Response (массив объектов):**
```json
[
  { "id": 1, "author": "aigerim", "likes": 340, "image": "cat.jpg" },
  { "id": 2, "author": "beka",    "likes": 21,  "image": "car.jpg" }
]
```
**UI:** вертикальная лента карточек. Каждый объект массива = одна карточка.
**Маппинг:** массив → цикл по карточкам; `author` → подпись, `likes` → счётчик лайков, `image` → картинка.
**Aha:** длина массива = число карточек. 2 объекта → 2 карточки. Добавили объект → появилась карточка.

**Диаграмма 1:** слева JSON-массив из 2 объектов, справа 2 карточки, стрелки поле→элемент.

---

### Сценарий 2 — Один объект (GET по id) ⭐ ядро
**Сайт:** YouTube страница видео / Kaspi карточка товара
**Endpoint:** `GET /videos/42`
**Response (один объект):**
```json
{
  "title": "Как работает API",
  "views": 15000,
  "channel": "IT для всех",
  "likes": 1200,
  "description": "В этом видео..."
}
```
**UI:** страница детали. Один объект = одна заполненная страница (не список).
**Маппинг:** `title` → крупный заголовок, `views` → «15 тыс. просмотров», `channel` → имя под видео, и т.д.
**Aha:** здесь НЕ массив, а один объект, потому что деталь одна. Список → массив, деталь → объект. Это прямое следствие REST (`/videos` список, `/videos/42` один).

**Диаграмма 2:** слева JSON-объект, справа макет страницы видео, стрелки к каждому полю.

---

### Сценарий 3 — Форма: создать новое (POST) ⭐ ядро
**Сайт:** регистрация / новый пост / добавить комментарий
**Здесь стрелка разворачивается: данные текут ОТ UI К серверу.**
**Endpoint:** `POST /users` (регистрация)
**Request body (что собрала форма):**
```json
{ "name": "Айгерим", "email": "a@mail.kz", "password": "..." }
```
**Response:** `201 Created`
```json
{ "id": 77, "name": "Айгерим", "email": "a@mail.kz" }
```
**UI:** форма с полями → кнопка «Зарегистрироваться» → успех/редирект.
**Маппинг (обратный!):** поле формы «Имя» → `name` в body; кнопка → отправка POST; `201` → показать успех; сервер вернул `id` → теперь пользователь существует.
**Aha:** в списке/детали данные шли сервер→UI. В форме наоборот: UI→сервер. Метод (`GET` vs `POST`) и определяет направление.

**Диаграмма 3:** форма слева, стрелка вправо к серверу с телом POST, назад стрелка `201 Created`.

---

### Сценарий 4 — Действие одной кнопкой: лайк (POST/DELETE) 🔵
**Сайт:** лайк на YouTube / сердечко в Instagram
**Endpoint:** `POST /videos/42/like` (поставить), `DELETE /videos/42/like` (убрать)
**Request/Response:** тело почти пустое, важен сам факт + статус
**UI:** серое сердечко → красное, счётчик +1.
**Aha:** даже одно нажатие сердечка это HTTP-запрос под капотом. UI меняется, потому что пришёл успешный ответ. Связь с идемпотентностью: два лайка не должны дать +2 (из HTTP-урока).

---

### Сценарий 5 — Поиск и фильтры (GET + query) 🔵
**Сайт:** 2GIS поиск / Kaspi фильтр товаров
**Endpoint:** `GET /products?category=phones&sort=price&q=samsung`
**Response:** массив (как сценарий 1, но отфильтрованный)
**UI:** строка поиска + фильтры → список результатов.
**Маппинг:** то, что вы вводите в поиск и фильтры, становится query-параметрами. Спиральный возврат к path vs query из HTTP-урока.
**Aha:** фильтры на странице = query-параметры в URL. Меняете фильтр → меняется endpoint → меняется список.

---

### Сценарий 6 — «Показать ещё» / пагинация 🔵 (упомянуть, не углубляться)
**Endpoint:** `GET /posts?page=2` (или cursor)
**Aha:** лента не грузит всё сразу. Кнопка «ещё» = следующий запрос со сдвигом. Бесконечная лента Instagram = автоматические GET по мере скролла.

## Диаграммы (3 основные, split-screen JSON ↔ UI)

| # | Слева | Справа | Стрелки |
|---|---|---|---|
| 1 | JSON-массив (2 объекта) | 2 карточки ленты | поле → элемент карточки, color-coded |
| 2 | JSON-объект видео | макет страницы видео | поле → заголовок/просмотры/канал |
| 3 | форма регистрации | сервер + `201` | UI → body POST → назад статус |

Стиль как в real-time: чистые, roughness 0, одна идея на диаграмму, текст ссылается на схему, не дублирует. Color-coding поля = ключевая фишка этих трёх.

- **Compare:** почему лента приходит как массив, а страница одного видео как объект?
